# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

A finished, working project: every milestone in `PLAN.md` (M1–M20) is done. Python backend in `backend/` (uv), React dashboard in `frontend/`, offline iPhone app in `mobile/` (reuses the frontend's pages), configuration in `config/` (alert rules, settings, your code descriptions), private raw exports in `data/` and databases in `db/` (both gitignored), synthetic `sample_data/` that is committed. `README.md` is the user-facing guide, `CONTRIBUTING.md` the contributor guide, `docs/data-dictionary.md` documents the files, tables and views, and `PLAN.md` keeps the decisions and what each milestone built.

Commands (from the repo root; the README has the full table): `make setup`, `make ingest` (loads `data/` into `db/mazda.duckdb`, idempotent, then evaluates alerts), `make dev` (API :8000 + Vite :5173), `make demo` (same with the synthetic data in its own database), `make model` (reload `config/codes/*.yaml` and `config/settings.yaml`, recreate views; **run it after changing views or config, and after pulling a version that changed `views.sql`**), `make timezone`, `make unmapped`, `make alerts`, `make types` (regenerate `frontend/src/api/schema.d.ts` after changing API models), `make test` / `make lint` (backend and frontend), `make mobile-test` (phone app against the Python API), `make mobile-pack`, `make mobile-dev` / `mobile-build`, `make format`, `make profile`, `make audit`, `make screenshots`, and `make reset-db` (deletes the database, alert acknowledgements included).

## Data overview (`data/`)

All files are telemetry/diagnostic exports for a single vehicle (one VIN, a Mazda "24PF" platform; the file names and row counts below are the author's export, other cars differ). Dates are in 2026. The CSVs are fully quoted, comma-separated with a header row; empty strings are common (missing values), so parse them as nulls rather than zeros.

| File | Rows | Contents |
|---|---|---|
| `all-war-24pf_war-24pf.csv` | ~7k | Warning events: trigger time, hours/minutes, odometer, `WARNING_LIST` (comma-separated `$`-prefixed hex codes, e.g. `$182,$21D`) |
| `all-dtc-d-24pf_dtc-d-24pf.csv` | ~1.1k | DTC events per ECU (`ECU_NAME_MKT`, `DISPLAY_DTC` like `U2701:89`, status flags) |
| `all-dtc-h-24pf_dtc-h-24pf.csv` | ~47 | DTC header/timing info (trigger time, odometer) |
| `all-dtc-ssr-24pf_dtc-ssr-24pf.csv` | ~137 | DTC snapshot records: very wide (hundreds of columns, mostly empty) freeze-frame data per DTC |
| `all-rts-24pf_rts-24pf.csv` | ~214 | Remote vehicle status snapshots (odometer, fuel, trip, etc.) as `<signal>_value` / `<signal>_validstatus` column pairs |
| `all-vis-24pf_vis-24pf.csv` | ~197 | Vehicle info status (door/lock/hood states) in the same `_value`/`_validstatus` pair format |
| `all-alt-24pf_alt-24pf.csv` | 4 | Alarm/burglar status |
| `all-24pf-diag-tool_…_20261015_090243.txt` | ~480 | Free-text "Collect Diagnostic Information" dump from a diagnostic tool (Mode 9 ECM data, VOD counters, OCC vehicle data sections) |

Things to know before writing parsing code:

- **Joining across files**: only `dtc-d` and `dtc-h` share `X_TRANSACTION_ID` (verified). `war` and `dtc-ssr` have their own ids and link to `dtc-h` via `WARNING_TRIGGER_OCCURRENCE_TM`. The `rts`/`vis`/`alt` files use lowercase column names (`vin`, `fileid_datetime`, `datacreationtime`) and have no transaction id — correlate them by timestamp. Full findings in `docs/data-dictionary.md`.
- **Sentinels**: `2147483647` / `4294967295` / odometer `-1` mean unknown; `dtc-ssr` is 404/487 empty columns.
- **Mixed timestamp formats**: `COPIED_DT_TM`/`fileid_datetime` are `YYYY-MM-DD HH:MM:SS` (no zone); `*_TM`/`datacreationtime` are ISO-8601 UTC (`…Z`). The diag-tool text file uses `UTC+0100` local time.
- **Signal value/validity pairs**: in `rts`/`vis`/`alt`, always check the sibling `_validstatus` column before trusting a `_value`.
- **`dtc-ssr`** snapshot columns include a `Time_UTC_Information_*` set split across Year/Month/Date/Hour/Minute fields.
- The diag-tool `.txt` is section-structured (`ModuleName:`, `VOD - …`, `… OCC Vehicle Data`, lines of `(KEY) = value [unit]`), not CSV.

## Backend architecture

`backend/src/mazda_dash/ingest/`: `schema.py` (DuckDB DDL), `csv_loaders.py` (SQL-based loaders, one per CSV kind, all via `_insert_new` = anti-join on the key + in-file dedupe), `diag_parser.py` (state-machine parser for the text dump, pure Python), `__init__.py` (file discovery by `*_<kind>-*.csv`, runner, CLI). Table keys and sentinel rules are in `docs/data-dictionary.md`. Tests use synthetic fixtures in `backend/tests/conftest.py`; run one with `cd backend && uv run pytest tests/test_ingest.py::test_dtc_kinds`. DuckDB 2.x: use `con.execute(...).fetchone()`, not `con.sql(...).fetchone()`.

`backend/src/mazda_dash/model/`: `lookups.py` loads and validates `config/codes/{warnings,dtcs,ecus,failure_types,warning_flags}.yaml` into `ref_*` tables and `settings.py` loads `config/settings.yaml` into `ref_settings`; `views.sql` defines all `v_*` views (executed as one script by `build_model`; `at` is a reserved word in DuckDB). `ingest()` calls `build_model` when given a config dir. View catalogue and the signal interpretations are in `docs/data-dictionary.md`. Code descriptions are user-maintained (Mazda does not publish them): never invent titles, leave `title: null`.

## API and frontend

`backend/src/mazda_dash/api/`: `app.py` (read-only FastAPI endpoints under `/api`, each a thin query over a `v_*` view), `models.py` (Pydantic response models = the OpenAPI contract), `db.py` (one short-lived read-only DuckDB connection per request so `make ingest` can write between calls; DB path from `MAZDA_DB`, default `../db/mazda.duckdb`; naive UTC timestamps are returned as explicit `...Z`). Add an endpoint by adding a model + route, then `make types` and the phone app's twin (see "Keep both implementations in step" below).

`frontend/` (Vite + React 19 + TypeScript): `src/api/hooks.ts` (typed `openapi-fetch` client + TanStack Query hooks; `schema.d.ts` and `openapi.json` are generated, do not edit), `src/pages/` (Overview, Trends, Alerts, Warnings, Faults, Status, Diagnostics), `src/components/ui.tsx` (Panel, Stat, sortable DataTable, QueryState), `src/lib.ts` (formatters; tests in `lib.test.ts`, run with `cd frontend && npm test`). Vite proxies `/api` to :8000. Styling is one hand-written `src/index.css` using CSS variables (dark default; light via `prefers-color-scheme` or the Auto/Dark/Light toggle, see Appearance below); fonts are bundled with `@fontsource` packages (imported in `src/main.tsx`; the phone app does the same in its own `main.tsx`), so neither app contacts another host. npm quirk: `frontend/.npmrc` sets `legacy-peer-deps` because plain `npm install` crashes with this dependency set, so peers such as `react-is` (needed by Recharts) must be listed explicitly.

## Alerts

`backend/src/mazda_dash/alerts/`: `config.py` (strict pydantic model of `config/alerts.yaml`; typos fail loudly), `detectors.py` (one function per rule, registry `DETECTORS`; rule names must match fields of `Rules`), `store.py` (`alerts` table, `add_if_new` keyed by `dedup_key`), `engine.py` (`run_alerts`), `notify.py` (optional macOS notification). Rules are raised once per `dedup_key` regardless of status, so acknowledged alerts never come back; event rules only look back `lookback_days` from the newest data point, state rules (`recurring_dtc`, `low_fuel`, `data_gap`, `oil_change_due`) evaluate the current state. The rules are `new_dtc`, `recurring_dtc`, `new_warning_code`, `warning_spike`, `burglar_alarm`, `high_consumption`, `low_fuel`, `low_tire_pressure`, `oil_change_due`, `car_warning_flag`, `new_warning_flag` and `data_gap`. To add a rule: model in `config.py` + detector + test in `tests/test_alerts.py`. The API lists/acknowledges alerts (`/api/alerts*`, the only write endpoints, using a short read-write connection that returns 503 while `make ingest` holds the lock); the UI page is `frontend/src/pages/Alerts.tsx`. Alerts live in the same DuckDB file, so `make reset-db` loses acknowledgements.

## Diagnostics and fault deep dives

API: `/api/diag/reports` (+ `/{id}`, `/{id}/frames`) and `/api/diag/compare?a=&b=` serve the diagnostic-tool dump (several reports can be ingested; the page gets a report picker and a comparison table automatically). `/api/dtcs/frames` gives a DTC's distinct freeze frames and `/api/dtcs/context?transaction_id=` the warnings (+/- N hours), other faults and closest status snapshot around a read-out. UI: `frontend/src/pages/Diagnostics.tsx` and `frontend/src/components/FaultDetail.tsx` (shown on the Faults page when a code is selected). The older `/api/dtcs/snapshots` endpoint is still served but unused by the UI.

## Sample data, audit and CI

Generated files that are committed (`sample_data/`, `frontend/openapi.json`, `schema.d.ts`) are compared byte for byte in CI on a UTC machine with no line-ending conversion: a generator must not use the machine's time zone, locale, `datetime.timestamp()` on naive times, or CRLF (a test covers the time zone; `.gitattributes` pins LF). To check CI parity: clone the repo, copy in your changes, `git add -A`, run `TZ=UTC make types sample-data` with `core.autocrlf=false`, then `git diff --exit-code`.

`backend/src/mazda_dash/sample.py` generates deterministic synthetic exports (`make sample-data` -> committed `sample_data/`; the VIN is `SAMPLEVIN00000001`, nothing comes from a real car). It is shaped to trigger every alert rule except `low_fuel` (`data_gap` fires because the data is old), so changing a detector or a view usually means checking `tests/test_sample.py` too. `make demo` ingests it into `db/demo.duckdb` and serves it. `mazda_dash/audit.py` (`make audit`) reads the VINs/positions from the real `data/` files and greps the publishable files and the full git history for them; never hardcode a real VIN anywhere to "check" for it. `.github/workflows/ci.yml` runs ruff, pytest, oxlint, tsc, vitest, the build, and checks that `make types sample-data` leave no diff. Charts honour `prefers-reduced-motion` via `ANIMATE` in `frontend/src/lib.ts`. README screenshots in `docs/screenshots/` are taken from the demo data by `docs/screenshots/capture.mjs` (`make screenshots`: headless Chrome through puppeteer-core, dark scheme, reduced motion, the clock set to 1 July 2026; it starts its own servers on :8000, :5173, :5174). Retake them when the UI changes visibly. The same script also draws `docs/social-preview.png` (1280×640, uploaded by hand in the repository's Settings → Social preview).

## Date range

Period-based endpoints take optional `from` / `to` query params (inclusive UTC days) through the `date_range` dependency in `backend/src/mazda_dash/api/dates.py`; `DateRange.clause(col)` returns the SQL fragment. A new period-based endpoint should use it and be added to `PERIOD_ENDPOINTS` in `tests/test_date_range.py`, which asserts that a range covering everything changes nothing and that an empty range returns empty results, not errors. State endpoints (active faults, alerts, diagnostics, code lookups) must not use it. Some views are re-aggregated inside the endpoint to honour the range (`fuel/monthly`, `warnings/frequency`, `dtcs/frequency`): keep them in step with `v_fuel_monthly`, `v_warning_frequency`, `v_dtc_frequency`. `dtcs/frequency` always lists faults that are active in the latest read-out. Frontend: the range lives in the URL (`frontend/src/range.ts`, `useDateRange`), every period-based hook in `api/hooks.ts` calls `useRangeQuery()` and puts it in its query key, and pages link with `RangeLink` / `RangeNavLink` so the range is carried along. `DateRangeBar` is rendered for the pages in `PERIOD_PAGES` in `App.tsx`. Pure helpers (`sanitizeRange`, `editRange`, `daysInRange`) are in `lib.ts` with tests.

Quick ranges (M9): the preset maths is pure and tested in `lib.ts` (`PRESETS`, `resolvePreset`, `matchPreset`, `restoreRange`); presets count back from the newest day with data (`/api/span`), inclusive, clamped to the first day. The URL always holds explicit `from`/`to`; which preset is highlighted is derived by matching, so there is no separate preset state to drift. The last choice is stored in `localStorage` (`cx5.range`: a preset id, `all` or `custom`) and `useRestoreSavedRange` (in `range.ts`, called from `App`) re-applies a saved preset once per page load, only when the address has no period. The bar uses native radio inputs for keyboard support.

## Trends (monthly comparison)

`backend/src/mazda_dash/api/trends.py` builds one row per calendar month in the period (`GET /api/trends/monthly`), from the events inside the period, with `days_covered` / `partial`; months without data stay in the series with `None` metrics (a gap, not 0). Distance is odometer-based (it matches `km_in_range`), consumption comes from trip segments, and "new faults" excludes anything first reported on the first diagnostic day. `tests/test_trends.py` pins these (including the gap and partial-month cases). All comparison logic lives in `frontend/src/trends.ts` (`METRICS` definitions with polarity, `metricValue`, `compare`, `describeChange`) and is unit tested; `pages/Trends.tsx` only renders. To add a metric: add the field to `MonthMetrics` and `monthly_metrics`, add a `MetricDef` (set `additive` for totals so "per day" works and `polarity` for the green/red colouring), and extend the tests.

## Several diagnostic reports (M10)

A report's id is a hash of the dump's content, so different dumps (even same date and VIN) are separate reports and an identical copy under another file name is skipped. `GET /api/diag/history` returns one headline row per report (oldest first) for the history table and charts (`components/ReportHistory.tsx`). The Diagnostics page keeps its selection in the URL (`?report=` and `?compare=`, via `pickReport` in `lib.ts`; an unknown id falls back to the newest report with a notice) and always orders a comparison from the earlier to the later report. `sample.py` writes three visits (`DIAG_VISITS`); changing them means updating `tests/test_diag_reports.py` and `tests/test_sample.py`.

## Offline phone app (`mobile/`)

`PLAN.md` ("Standalone offline app for iPhone") has the design and the measurements behind it. `backend/src/mazda_dash/pack.py` exports the database as a `.cx5pack` (Parquet tables + manifest; GPS positions excluded; `--reference` adds per-view fingerprints used by tests). `mobile/` loads it into DuckDB-WASM in the browser, rebuilds every view from `views.sql`, and answers the pages' `/api/...` requests with a TypeScript port of the API. `*.cx5pack` files contain a VIN: they are gitignored and must never be served on the network or deployed (only `mobile/public/demo.cx5pack`, built from the synthetic data, is). The Mac app (`frontend/`, `backend/`) is the reference and works without `mobile/`.

M13 added `mobile/src/engine/`, the Python API re-implemented in TypeScript on DuckDB-WASM. **Any change to an endpoint, its SQL, its response model or `views.sql` in `backend/` must be mirrored there** (`api.ts` routes, the handler files, `shapes.ts` for model fields), then checked with `make mobile-test`: it records what the Python API answers on the sample data (`make mobile-golden` → `mobile/contract/`, gitignored) and replays it on the TypeScript engine; `make mobile-golden-real` does the same on your own database (delete `mobile/contract/real` afterwards, it holds your VIN). Give every `ORDER BY` a tie-breaker. The pack keeps whole every signal source except `rts`; `views.sql` may name `rts` signals only as `signal = '<name>'` (or a family with `starts_with`, see M20).

M14 added the app itself in `mobile/src`: `main.tsx` wires `DataController` (`controller.ts`, UI-free: engine start, stored pack, import/replace/delete, acks replay), IndexedDB `storage.ts`, `engine-browser.ts` (DuckDB-WASM in a worker, queries run one at a time) and `App.tsx` (bottom tab bar) around the pages of `frontend/src` (alias `@frontend`). The hooks reach the API only through `frontend/src/api/client.ts`; the phone replaces its `fetch` with `setFetch(createFetch(api))`, so **frontend code must keep using that client and never call `fetch` for `/api` directly**, and must not load anything from another host (the phone app promises no outside request; fonts are bundled). `make mobile-dev` / `mobile-build` / `mobile-test`.

M15: `vite.config.ts` generates `dist/sw.js` from `sw.template.js` (precache list + content-hash version; never edit `dist/`); `src/pwa.ts` registers it in production builds only and drives the update prompt; `controller.ts` also asks for persistent storage and remembers (`localMemory`) that data existed, to tell evicted data from a first run. Shared CSS changes for phones live in `frontend/src/index.css` under `max-width: 640px` / `pointer: coarse` queries and must leave desktop widths unchanged; `DateRangeBar` has a narrow-screen toggle. A new file the app loads at run time must come from the build output (or `mobile/public/`), otherwise the service worker will not cache it and the app breaks offline. The iOS Simulator reaches `localhost`, so `make mobile-build` + `npm run preview` there tests install and offline (stop the server and reload).

**Keep both implementations in step (M16).** Adding or changing an API route, its SQL, its response model, `views.sql`, or what the pack exports means changing the Python API, the TypeScript engine (`mobile/src/engine/`: route in `api.ts`, handler, `shapes.ts`) and, if needed, the golden matrix in `backend/src/mazda_dash/contract.py`, in one change; `make mobile-test` must pass (CI runs it in the `mobile` job, and a Python test fails when a route has no golden case). Hosting: `.github/workflows/pages.yml` publishes `mobile/dist` (app + synthetic demo pack only) to GitHub Pages after `make mobile-test`; both it and CI fail if `dist` holds any `.cx5pack` other than `demo.cx5pack`, and `make audit` fails on any non-ignored `*.cx5pack`. Never commit or deploy a real pack.

Appearance (Auto / Dark / Light): `frontend/src/theme.ts` (choice in `localStorage` `cx5.theme`, applied as `data-theme` on `<html>`; both `index.html` files apply it before first paint and carry two `theme-color` metas) with `components/ThemeToggle.tsx` (segmented control in the Mac rail, `ThemeCycleButton` as the last cell of the phone tab bar). In `index.css` the light palette exists twice (device in light mode and not forced dark, and forced light) because CSS cannot share one block across a media query and an attribute selector; `theme.test.ts` fails if they differ. Add a new colour variable to the dark block and BOTH light blocks. Use `var(--...)` for colours, never literals, so both themes work.

Settings (`config/settings.yaml`: `car_timezone`, `tire_stale_hours`) are loaded by `model/settings.py` into `ref_settings`; views read them (`v_tire_snapshots`), the pack carries the table, and the phone app has no copy of the values. Time zone conversion lives in SQL (ICU) so Python and the phone cannot disagree: use one `make_timestamp(epoch_us(timezone(zone, ts)))`, never nested `timezone(...)` calls (the in-browser DuckDB cannot run them), and do not depend on the session TimeZone. `tire` views use the column name `reading_at` because `at` is reserved. Hard time cases (clock changes, impossible dates) are added to the golden database in `contract.py` (`TIRE_CLOCK_EDGE_CASES`), not to the sample files. `make timezone` checks the configured zone.

Warning-lamp flags (M20): the 128 `vdt_*` columns are read as a signal *family* with `starts_with(signal, 'vdt_2_warningpt_')`; `pack.py` finds such prefixes (`used_signal_prefixes`) and exports only family members with more than one value (`varying_in_families`, which must stay identical to the `varying` test in `v_warning_flag_readings`: a view that listed constants would differ in the pack). Do not write signal lists as `signal IN (...)` or `LIKE` in `views.sql` (a test forbids it); use `signal = '<name>'` for single signals and `starts_with` for families, and the phone refuses packs lacking a family. Hints are shown as hints: never present a co-occurrence as the meaning of a flag, and never invent titles in `config/codes/warning_flags.yaml`.
