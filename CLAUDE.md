# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Current state

**Mazda Data Dashboard** (the project's name since it handles several car models; the `cx5.*` storage keys, the `.cx5pack` extension and the phone's IndexedDB `cx5` keep their old names on purpose). A finished, working project: every milestone in `PLAN.md` up to M39 is done except M28 (adapting to a real CX-60 export: conditional, not started); M40–M41 (the car in 3D on the phone, per-model shape) are planned. Python backend in `backend/` (uv), React dashboard in `frontend/`, offline iPhone app in `mobile/` (reuses the frontend's pages), configuration per car model in `config/models/<id>/` (alert rules, settings, your code descriptions; the model list is `config/models.yaml`), private raw exports in `data/<id>/` and databases in `db/<id>.duckdb` (both gitignored), synthetic `sample_data/<id>/` that is committed. The project supports several Mazda models (CX-5 real, CX-60 synthetic so far): see "Car models". `README.md` is the user-facing guide, `CONTRIBUTING.md` the contributor guide, `docs/data-dictionary.md` documents the files, tables and views, and `PLAN.md` keeps the decisions and what each milestone built.

Commands (from the repo root; the README has the full table): `make setup`, `make ingest` (loads `data/<id>/` into `db/<id>.duckdb`, idempotent, then evaluates alerts), `make dev` (API :8000 + Vite :5173), `make demo` (same with the synthetic data in its own database), `make model` (reload each model's `config/models/<id>/codes/*.yaml` and `settings.yaml`, recreate views; **run it after changing views or config, and after pulling a version that changed `views.sql`**), `make timezone`, `make unmapped`, `make alerts`, `make compat`, `make models`, `make migrate-models`, `make types` (regenerate `frontend/src/api/schema.d.ts` after changing API models), `make test` / `make lint` (backend and frontend), `make mobile-test` (phone app against the Python API), `make mobile-pack`, `make mobile-dev` / `mobile-build`, `make format`, `make profile`, `make audit`, `make screenshots`, and `make reset-db` (deletes the database, alert acknowledgements included).

## Car models (M21)

`backend/src/mazda_dash/models.py` is the registry: `config/models.yaml` lists the model ids, `config/models/<id>/model.yaml` describes one (`id` = folder name, `name`, `platform`, `pages` to hide, `default`), and `load_registry()` validates them and returns `Model` objects with `data_dir` (`data/<id>/`), `db_path` (`db/<id>.duckdb`), `config_dir` (`config/models/<id>/`: `settings.yaml`, `alerts.yaml`, `codes/`) and `pack_path`. One DuckDB file per model, nothing shared (descriptions of codes never fall back to another model); one car per model folder. The single-car layout (`data/*.csv`, `db/mazda.duckdb`) is still read as `cx5` until `make migrate-models`. Every CLI takes `--model` (default: the default model) and still lets `--data/--db/--config` override; the Makefile loops over `MODELS` (all, or `MODEL=<id>`). Anything that needs a path to a model's data, database or config goes through `models.py`, never a hard-coded `../data` or `../db/mazda.duckdb`. `MAZDA_DB` overrides the *default model's* database only (tests), and `MAZDA_DB_PREFIX=demo-` moves every database to `db/demo-<id>.duckdb` (the demo). `compat.py` (`make compat`) compares the signals `views.sql` reads (`pack.used_signals` / `used_signal_prefixes`) with a model's `signal_readings`; ingest warns about an empty folder (no database is created for it) and about several VINs in one database; alert notifications carry the model's name. A model's missing `alerts.yaml` / `settings.yaml` falls back to the built-in defaults in `alerts/config.py` / `model/settings.py` (there is no shared `config/defaults/`). `tests/test_model_isolation.py` builds two models and asserts that data, code descriptions, time zones and alerts never mix; keep it passing when touching ingest or config loading. The API (M23) and the Mac dashboard (M24, below) are model-aware; the phone app too (M26, see "Offline phone app"); `sample_data/<model>/` holds a synthetic set per model (M25, below). `make audit` reads `data/` recursively, so every model's folder is covered, and it fails when `sample_data/<id>/` holds anything but the synthetic VINs (no real VIN or position). Adding a model: the README's "How to add a model", which `tests/test_add_a_model.py` follows step by step (keep the two in step). The design and what each milestone built: `PLAN.md`, "Several car models".

## Data overview (`data/`)

All files are telemetry/diagnostic exports for a single vehicle (one VIN, a Mazda "24PF" platform; the file names and row counts below are the author's export, other cars differ). Dates are in 2026. The CSVs are fully quoted, comma-separated with a header row; empty strings are common (missing values), so parse them as nulls rather than zeros.

| File | Rows | Contents |
|---|---|---|
| `all-war-24pf_war-24pf.csv` | ~7k | Warning events: trigger time, hours/minutes, odometer, `WARNING_LIST` (comma-separated `$`-prefixed hex codes, e.g. `$182,$21D`) |
| `all-dtc-d-24pf_dtc-d-24pf.csv` | ~1.1k | DTC events per ECU (`ECU_NAME_MKT`, `DISPLAY_DTC` like `U2701:89`, status flags) |
| `all-dtc-h-24pf_dtc-h-24pf.csv` | ~47 | DTC header/timing info (trigger time, odometer) |
| `all-dtc-ssr-24pf_dtc-ssr-24pf.csv` | ~137 | DTC snapshot records: very wide (hundreds of columns, mostly empty) freeze-frame data per DTC |
| `all-rts-24pf_rts-24pf.csv` | ~214 | Remote vehicle status snapshots (odometer, fuel, trip, etc.) as `<signal>_value` / `<signal>_validstatus` column pairs |
| `all-vis-24pf_vis-24pf.csv` | ~197 | Vehicle info status (door/lock/hood states) in the same `_value`/`_validstatus` pair format |
| `all-alt-24pf_alt-24pf.csv` | 4 | Alarm/burglar status |
| `all-24pf-diag-tool_…_20261015_090243.txt` | ~480 | Free-text "Collect Diagnostic Information" dump from a diagnostic tool (Mode 9 ECM data, VOD counters, OCC vehicle data sections) |

Things to know before writing parsing code:

- **Joining across files**: only `dtc-d` and `dtc-h` share `X_TRANSACTION_ID` (verified). `war` and `dtc-ssr` have their own ids and link to `dtc-h` via `WARNING_TRIGGER_OCCURRENCE_TM`. The `rts`/`vis`/`alt` files use lowercase column names (`vin`, `fileid_datetime`, `datacreationtime`) and have no transaction id — correlate them by timestamp. Full findings in `docs/data-dictionary.md`.
- **Sentinels**: `2147483647` / `4294967295` / odometer `-1` mean unknown; `dtc-ssr` is 404/487 empty columns.
- **Mixed timestamp formats**: `COPIED_DT_TM`/`fileid_datetime` are `YYYY-MM-DD HH:MM:SS` (no zone); `*_TM`/`datacreationtime` are ISO-8601 UTC (`…Z`). The diag-tool text file uses `UTC+0100` local time.
- **Signal value/validity pairs**: in `rts`/`vis`/`alt`, always check the sibling `_validstatus` column before trusting a `_value`.
- **`dtc-ssr`** snapshot columns include a `Time_UTC_Information_*` set split across Year/Month/Date/Hour/Minute fields.
- The diag-tool `.txt` is section-structured (`ModuleName:`, `VOD - …`, `… OCC Vehicle Data`, lines of `(KEY) = value [unit]`), not CSV.

## Backend architecture

`backend/src/mazda_dash/ingest/`: `schema.py` (DuckDB DDL), `csv_loaders.py` (SQL-based loaders, one per CSV kind, all via `_insert_new` = anti-join on the key + in-file dedupe), `diag_parser.py` (state-machine parser for the text dump, pure Python), `__init__.py` (file discovery by `*_<kind>-*.csv`, runner, CLI). Table keys and sentinel rules are in `docs/data-dictionary.md`. Tests use synthetic fixtures in `backend/tests/conftest.py`; run one with `cd backend && uv run pytest tests/test_ingest.py::test_dtc_kinds`. DuckDB 2.x: use `con.execute(...).fetchone()`, not `con.sql(...).fetchone()`.

`backend/src/mazda_dash/model/`: `lookups.py` loads and validates `config/models/<id>/codes/{warnings,dtcs,ecus,failure_types,warning_flags}.yaml` into `ref_*` tables and `settings.py` loads `config/models/<id>/settings.yaml` into `ref_settings`; `views.sql` defines all `v_*` views (executed as one script by `build_model`; `at` is a reserved word in DuckDB). `ingest()` calls `build_model` when given a config dir. View catalogue and the signal interpretations are in `docs/data-dictionary.md`. Code descriptions are user-maintained (Mazda does not publish them): never invent titles, leave `title: null`.

## API and frontend

`backend/src/mazda_dash/api/`: `app.py` (read-only FastAPI endpoints under `/api`, each a thin query over a `v_*` view; `GET /api/garage` composes three of them, see "All cars"), `models.py` (Pydantic response models = the OpenAPI contract), `selection.py` (the `model` dependency) and `db.py` (one short-lived read-only DuckDB connection per request so `make ingest` can write between calls, on the database of the model the request names; `MAZDA_DB` replaces the default model's database only, `MAZDA_ROOT` points at another repository root, both for tests and the demo; naive UTC timestamps are returned as explicit `...Z`). Add an endpoint by adding a model + route, then `make types` and the phone app's twin (see "Keep both implementations in step" below).

`frontend/` (Vite + React 19 + TypeScript): `src/api/hooks.ts` (typed `openapi-fetch` client + TanStack Query hooks; `schema.d.ts` and `openapi.json` are generated, do not edit), `src/pages/` (Overview, Trends, Compare + ComparePeriods, Garage = "All cars", Alerts, Warnings, Faults, Status, Diagnostics), `src/components/ui.tsx` (Panel, Stat, sortable DataTable, QueryState), `src/lib.ts` (formatters and the model/range helpers), `src/trends.ts`, `src/compare.ts`, `src/garage.ts` (pure logic), `src/model.ts` and `src/range.ts` (the model and the period in the address); every `*.ts` next to them has a `*.test.ts` (run with `cd frontend && npm test`). Vite proxies `/api` to :8000. Styling is one hand-written `src/index.css` using CSS variables (dark default; light via `prefers-color-scheme` or the Auto/Dark/Light toggle, see Appearance below); fonts are bundled with `@fontsource` packages (imported in `src/main.tsx`; the phone app does the same in its own `main.tsx`), so neither app contacts another host. npm quirk: `frontend/.npmrc` sets `legacy-peer-deps` because plain `npm install` crashes with this dependency set, so peers such as `react-is` (needed by Recharts) must be listed explicitly.

## Alerts

`backend/src/mazda_dash/alerts/`: `config.py` (strict pydantic model of `config/models/<id>/alerts.yaml`; typos fail loudly), `detectors.py` (one function per rule, registry `DETECTORS`; rule names must match fields of `Rules`), `store.py` (`alerts` table, `add_if_new` keyed by `dedup_key`), `engine.py` (`run_alerts`), `notify.py` (optional macOS notification). Rules are raised once per `dedup_key` regardless of status, so acknowledged alerts never come back; event rules only look back `lookback_days` from the newest data point, state rules (`recurring_dtc`, `low_fuel`, `data_gap`, `oil_change_due`) evaluate the current state. The rules are `new_dtc`, `recurring_dtc`, `new_warning_code`, `warning_spike`, `burglar_alarm`, `high_consumption`, `low_fuel`, `low_tire_pressure`, `oil_change_due`, `car_warning_flag`, `new_warning_flag`, `low_battery_frame` and `data_gap`. To add a rule: model in `config.py` + detector + test in `tests/test_alerts.py`. The API lists/acknowledges alerts (`/api/alerts*`, the only write endpoints, using a short read-write connection that returns 503 while `make ingest` holds the lock); the UI page is `frontend/src/pages/Alerts.tsx`. Alerts live in the same DuckDB file, so `make reset-db` loses acknowledgements.

**Every route takes the optional `model` query parameter (M23)**, because `get_con` / `get_rw_con` depend on `get_model` (omitted = the default model, unknown id = 404 listing the valid ones, broken model config = 503). A route that needs a database must use `Con` / `RwCon` (or `Selected`), never open a file itself; `tests/test_api_models.py` fails when a route lacks the parameter and checks that two models answer differently, that acknowledging alerts in one model leaves the other alone, and that `MAZDA_DB` never answers for another model. `GET /api/models` lists the models with `has_data` and their first/last day (the dashboard's switcher reads it in M24); it, like `/api/health`, has no golden case because the phone answers for itself (a stored pack is one model, M26). The TypeScript engine answers for the one pack it has loaded and refuses another model with the same 404 (M26).

**Dashboard model switcher (M24).** The model lives in the address next to the period (`?model=cx60`; none = the default model, so a default-model address stays clean) and `useModelParam()` (in `range.ts`) reads it. `useRangeQuery()` in `api/hooks.ts` returns `{from, to, model}`: spread into the request and used in the query key, so a hook can never show another model's cached figures; **every new hook must take the model from it (or `useRangeQuery().model`) in both the request and the key**, and `RangeLink` / `RangeNavLink` carry `model` with the period. `model.ts`: `useCurrentModel()` (list from `GET /api/models`, the chosen model, `notFound`; when the route is missing it falls back to "Mazda CX-5" and no switcher; the phone answers it from its stored packs), `useSwitchModel()` (re-counts presets from the new model's newest day or clamps typed dates with `rangeForModel`, drops `?report=` and `?compare=`, remembers the choice in `localStorage` `cx5.model`) and `useRestoreSavedModel()` (once per load; `useRestoreSavedRange(ready)` waits for it **and for the address to show the model**, otherwise it builds on the old address and drops the model again; react-router's `setParams` updater works from the last rendered address). Pure helpers with tests in `lib.ts`: `pickModel`, `restoreModel`, `rangeForModel`, `isPageHidden` / `PAGE_PATHS`, `shortModelName`. `App.tsx`: `ModelSwitcher` (native select in the rail, only with 2+ models that have data, each entry with that car's new alerts, "(no data yet)" only for a model the address names), `ModelGate` (unknown model, model without data: a message instead of the pages), pages hidden by `pages:` in `model.yaml` leave the nav and redirect to the overview, and `<Routes key={id}>` remounts the pages on a switch so nothing a page remembers (a chosen fault or flag) crosses models. UI text that names config files uses the model id (`useCurrentModel().id`), never a literal `cx5`.

**Compare two cars (M29).** `frontend/src/pages/Compare.tsx` (`/compare?mode=cars&a=&b=&basis=all&perday=0&partial=1`) reads `GET /api/trends/monthly?model=` twice through `useMonthlyOf(model)` (a model's whole history, no period; no backend change). All the logic is pure and tested in `frontend/src/compare.ts` and works on `Series` (a label and monthly rows, not models, so comparing two periods of one car can reuse it): `alignMonths` (calendar months, only months both cars have *complete* by default, `all` = union with gaps, never zeros), `summarise` (mean of monthly values weighted by what they cover: days for per-day totals, distance for l/100 km, driving time for average speed), `compareMetric` (on the overlap basis only months where both cars have a value for that metric, so both figures stand on the same months), `describeDifference` (neutral: "higher" and "lower", the figures and the month count, a test forbids verdict words) and `COMPARABILITY`, a table with a level (`comparable` / `caution` / `no`) and a reason **for every metric: a new metric in `trends.ts` must get an entry** (a test fails otherwise). No good/bad tone colours on this page (a different car is not an improvement); the two cars differ by colour, marker shape and dash. The two-cars view needs two models that have data and show the Trends page; the nav entry itself shows with one (see M31).

**Compare on the phone (M30).** The Compare page itself is shared (`frontend/src/pages/Compare.tsx`); the phone's engine holds one pack at a time, so `DataController` caches each stored car's **summary** (the engine's own answers to `/api/trends/monthly` without a period and, since M32, `/api/garage`) in the IndexedDB store `summaries` (storage v3), keyed `<SUMMARY_VERSION>:<pack savedAt>` per model (**raise `SUMMARY_VERSION` in `controller.ts` whenever the monthly or garage answer's fields or maths change**, or a stale summary would be shown; replacing or deleting a pack discards it). A summary is made when a car is loaded (`activate`) and `prepareComparison()` loads the cars that have none, one after the other, then the car that was shown (status `loading` and `preparing: true` throughout; `useFollowTheAddress` stays quiet while `preparing`). `Api.setSummaries` lets the engine answer `GET /api/trends/monthly?model=<other>` **only without `from`/`to`** from a summary; everything else about another model is still the 404. `SummaryGate` (mobile; it also guards All cars) prepares the cars before showing the page and shows a failure once instead of retrying; the entry is "Compare" under More. Tests: `test/controller.test.ts` (summaries, prepare, stale, replace, delete) and `test/engine.test.ts`.

**Two periods of one car (M31).** `Compare.tsx` is now a shell with a *Two cars* | *Two periods* switch (`?mode=`; with one car that has data it starts on periods) around `CarsCompare` (M29) and `ComparePeriods.tsx`. Periods are of **the car on screen** (change the car with the model selector; on the phone only the loaded car can answer a period), fetched with `useMonthlyRange(model, from, to)` = `GET /api/trends/monthly` with `from`/`to` (a month cut by the period only counts its days inside it): **no new route, no phone engine change**. The maths is in `compare.ts`: `summarisePeriod` (totals add up, rates are weighted by what they are a rate of, the lowest tire reading is the lowest of the months), `comparePeriods` (neutral words from `describeDifference` **plus a good/bad tone from the metric's polarity: tones exist only here, never between two cars**), `PERIOD_UNAVAILABLE` (the number of different warning codes or faults cannot be added up from months: shown as not compared), `periodPresets` (counted back from the newest day with data; a pair whose periods have no data is disabled), `validatePeriods` (a period with no data blocks, an overlap only warns), `periodLabel`, `yearAgo`. The state is in the address (`preset`, `around`, `af`/`at`/`bf`/`bt`, `perday`). Cost per 100 km and the average tire pressure are now weighted (by distance, by days) in the two-cars view too. The nav entry shows with one car that has data.

**All cars (M32).** `GET /api/garage` (Python `garage()` in `api/app.py` and `mobile/src/engine/garage.ts`, with goldens) is one car's headline card: it calls the overview for the 30 days up to the newest day with data (never before the first day), the oil countdown and the car's own warnings, so it can never disagree with those pages. Since M34 it also carries the window's **fuel and cost** (`fuel_l_30d`, `l_per_100km_30d`, `fuel_cost_30d`, `cost_per_100km_30d`, `currency`): estimates built from the overview's `km_in_range` and its average consumption and cost per 100 km (`_fuel_and_cost` in Python, `fuelAndCost` in TypeScript, kept identical), the cost null without a fuel price; for a window that is a whole month they equal that month's Trends figures (a test pins it); `has_data: false` for an empty database. The page is `frontend/src/pages/Garage.tsx` (one `Card` per model with data via `useGarageOf`, the wording and the one-week stale rule in `garage.ts`, tested), the nav entry shows with one or more cars that have data, and `ModelSwitcher` shows each car's new alerts through the same `garageQuery` (invalidated when alerts are acknowledged). "Show <car>" is `useSwitchModel()(id, '/')`: **change the model and the page in ONE navigation** (two separate ones race and the second drops the first one's parameters). On the phone `summaries` hold `{monthly, garage}` per car (`SUMMARY_VERSION` 3), `Api.setSummaries` answers `/api/garage?model=<other>` from the cache, `SummaryGate` (Compare and All cars) prepares them, and the controller **refreshes a car's cached card when another car replaces it** (`refreshGarage`: alerts may have been acknowledged since).

## When the car is used (M35)

`v_activity_events` (views.sql) lists warnings and close drives with their local time (`car_timezone`; UTC to local is **one** `timezone(zone, make_timestamptz(epoch_us(ts)))`, the browser's DuckDB cannot bind nested `timezone()` calls). `GET /api/activity/pattern` (Python `activity_pattern`, TypeScript `mobile/src/engine/activity.ts`, identical SQL, a period endpoint in `PERIOD_ENDPOINTS` whose empty answer is an object with empty `hours`/`weekdays`) returns hours (0–23: days with activity, distinct warning codes, km, drives) and weekdays (calendar days, days with activity, km). It is deliberately **per day, not per event**: the raw counts mislead because the warnings table is mostly repeats and a weekday can simply have more days in the period. The UI is `frontend/src/components/WhenPanel.tsx` on Status with the pure wording in `frontend/src/activity.ts` (neutral, buckets under `MIN_DAYS` marked "few days"). 

**Fault context from freeze frames (M36).** `v_frame_signals` gives one value per signal of each DISTINCT freeze frame (the same frame is re-reported in later read-outs). `GET /api/dtcs/frame-summary?ecu=&dtc_code=` (Python `frame_summary`, TypeScript `mobile/src/engine/framesummary.ts`, identical SQL, a state endpoint) compares one fault's frames with all OTHER faults' frames for battery voltage (both supply signals), battery charge, coolant temperature and speed: min/median/max of each, the baseline's range and 10th/90th percentile, and a `position` (`low`/`high`) only with at least 10 baseline frames and some spread. The signal list lives in `FRAME_SUMMARY_SIGNALS` (Python) and `SIGNALS` (TypeScript): keep them equal. UI: `frontend/src/components/FrameSummary.tsx` at the top of `FaultDetail`, wording in `frontend/src/frames.ts` ("tends to appear when ...", never a cause, a caution under `FEW_FRAMES` = 5 frames). The alert `low_battery_frame` (`alerts/detectors.py`, `min_voltage` default 12.0 V in `alerts.yaml`, severity warning) raises once per fault when a frame inside the lookback window recorded a supply voltage below the limit. 
**Who rides (M37).** `v_occupancy` (views.sql) has the seat belts of each status snapshot (`firstrowbuckledriver`, `firstrowbucklepsngr`, `rear_left_seatbelt_used`, `rear_right_seatbelt_used`, each named as `signal = '...'` so the pack carries them). `GET /api/status/occupancy` (Python `occupancy`, TypeScript `mobile/src/engine/occupancy.ts`, identical SQL, a period endpoint whose empty answer is `available: false`) counts, among snapshots with the **driver's belt buckled** (the car in use: `enginestate` is undocumented, so it is not used), those with the front passenger's or a rear belt buckled too, in total and per month. The UI is `frontend/src/components/WhoRidesPanel.tsx` on Status (hidden when the car sends no belts), wording in `frontend/src/occupancy.ts`. Never read: the third-row belts (a CX-5 has none) and the seat-sensor status (undocumented). The sample generator gives the CX-60 the belts through `Profile.belts` (from the odometer, no random numbers) and the CX-5 does not, so the CX-5 sample bytes did not change; the compat report lists the four belt signals as missing for the CX-5 sample.

**The car, part by part (M38) and in 3D (M39; phone M40 and per-model shape M41 are planned, see `PLAN.md` "The car in 3D").** `frontend/src/car.ts` (pure, tested) turns the answers of four existing endpoints (`/api/overview`, `/api/doors/timeline?limit=1`, `/api/maintenance/oil`, `/api/status/car-warnings`; **no route of its own, so nothing to mirror on the phone**) into thirteen parts (four wheels, four doors, trunk, hood, fuel, engine, dash), each with a state (`ok` / `attention` / `open` / `unknown` / `absent`), a figure and notes. `components/CarPanel.tsx` lists them at the top of Status (it replaced the Doors panel); `CarList` is meant to stay as the fallback and text equivalent of the 3D view. Rules to keep: a value the car flagged Invalid is `unknown`, never closed or zero; what a car does not send is `absent` and not listed; **no invented limits** (a part is marked only by the car's own flag, the `LOWEST_SPREAD_KPA` rule shared with `Tires.tsx`, or `OIL_SOON_KM`); lock codes stay raw. The 3D scene draws from `carState`, never from the endpoints directly, so list and drawing cannot disagree.

`frontend/src/car3d/` is the 3D view: `geometry.ts` (the schematic SUV from a `Body` of dimensions; axes: front +x, up +y, the car's right +z; a generic shape, **never a Mazda mesh or model file**), `orbit.ts` (own camera maths: no OrbitControls) and `labels.ts` are pure and tested; `scene.ts` (`CarScene`) is the only three.js code and `Car3D.tsx` hosts it with the labels as HTML over the canvas. **`three` must stay in the lazy chunk**: only `scene.ts` and `Car3D.tsx` may import it and only `CarPanel` loads them, with `lazy()` (a test in `labels.test.ts` fails otherwise); `three` is a dependency of both `frontend/` and `mobile/` (the phone build bundles and precaches the chunk). Keep: rendering on demand (no render loop), colours from the CSS variables via `readPalette` (re-read on a theme change), the plain mouse wheel left to the page (zoom is Ctrl/Cmd + wheel, keys, buttons), `touch-action: pan-y` with a finger turning sideways only, and the list as the fallback (no WebGL, lost context, failed chunk) and on screens of 640 px and under until M40. A new part needs an entry in `car.ts`, an anchor in `geometry.ts` and, if it is drawn, a mesh in `scene.ts`.

## Sample data, audit and CI

Generated files that are committed (`sample_data/`, `frontend/openapi.json`, `schema.d.ts`) are compared byte for byte in CI on a UTC machine with no line-ending conversion: a generator must not use the machine's time zone, locale, `datetime.timestamp()` on naive times, or CRLF (a test covers the time zone; `.gitattributes` pins LF). To check CI parity: clone the repo, copy in your changes, `git add -A`, run `TZ=UTC make types sample-data` with `core.autocrlf=false`, then `git diff --exit-code`.

`backend/src/mazda_dash/sample.py` generates deterministic synthetic exports (`make sample-data` -> committed `sample_data/<model>/`; nothing comes from a real car). It is driven by a `Profile` per model (`CX5`, `CX60` in `PROFILES`: platform code in the file names, VIN `SAMPLEVIN0000000N`, period, time zone, tank and consumption, which tire leaks, warning codes, faults, diagnostic visits and their clock, whether the car sends the oil countdown, extra signals); **the CX-5 profile must keep producing the committed bytes** (a new feature that adds data to every car shifts the random stream: derive it from the clock, and give a model a profile flag when it should lack it). The CX-60 is another car on purpose (other platform code `sample60`, VIN, 10 Apr–31 Jul, Europe/Berlin and a UTC+0200 diagnostic tool, front-left leak, two reports, no oil countdown, two signals the CX-5 lacks), and `tests/test_sample_models.py` pins the differences, that the committed files equal the generator's output for every model, and time zone independence for each. The model selector lists only models that have data (a set-up model nobody loaded yet stays out, unless the address names it), so a CX-5-only install shows no selector; `make model`, `alerts`, `timezone`, `unmapped`, `compat` and `mobile-pack` skip models without a database (`models ids --with-db`). A new model profile also needs `config/models/<id>/` and a line in `config/models.yaml`. It is shaped to trigger every alert rule except `low_fuel` (`data_gap` fires because the data is old), so changing a detector or a view usually means checking `tests/test_sample.py` too. `make demo` ingests every model's set into its own `db/demo-<model>.duckdb` (`MAZDA_DB_PREFIX=demo-`, which also turns the single-car fallback off, so your own databases are never touched) and serves them all with the model selector. `mazda_dash/audit.py` (`make audit`) reads the VINs/positions from the real `data/` files and greps the publishable files and the full git history for them; never hardcode a real VIN anywhere to "check" for it. `.github/workflows/ci.yml` runs ruff, pytest, oxlint, tsc, vitest, the build, and checks that `make types sample-data` leave no diff. Charts honour `prefers-reduced-motion` via `ANIMATE` in `frontend/src/lib.ts`. README screenshots in `docs/screenshots/` are taken from the demo data by `docs/screenshots/capture.mjs` (`make screenshots`: headless Chrome through puppeteer-core, dark scheme, reduced motion, the clock set to 1 July 2026, or 1 August for the CX-60 and All cars shots; it starts its own servers on :8000, :5173, :5174). Retake them when the UI changes visibly. The same script also draws `docs/social-preview.png` ("Mazda Data Dashboard", 1280×640, uploaded by hand in the repository's Settings → Social preview).

## Date range

Period-based endpoints take optional `from` / `to` query params (inclusive UTC days) through the `date_range` dependency in `backend/src/mazda_dash/api/dates.py`; `DateRange.clause(col)` returns the SQL fragment. A new period-based endpoint should use it and be added to `PERIOD_ENDPOINTS` in `tests/test_date_range.py`, which asserts that a range covering everything changes nothing and that an empty range returns empty results, not errors. State endpoints (active faults, alerts, diagnostics, code lookups) must not use it. Some views are re-aggregated inside the endpoint to honour the range (`fuel/monthly`, `warnings/frequency`, `dtcs/frequency`): keep them in step with `v_fuel_monthly`, `v_warning_frequency`, `v_dtc_frequency`. `dtcs/frequency` always lists faults that are active in the latest read-out. Frontend: the range lives in the URL (`frontend/src/range.ts`, `useDateRange`), every period-based hook in `api/hooks.ts` calls `useRangeQuery()` and puts it in its query key, and pages link with `RangeLink` / `RangeNavLink` so the range is carried along. `DateRangeBar` is rendered for the pages in `PERIOD_PAGES` in `App.tsx`. Pure helpers (`sanitizeRange`, `editRange`, `daysInRange`) are in `lib.ts` with tests.

Quick ranges (M9): the preset maths is pure and tested in `lib.ts` (`PRESETS`, `resolvePreset`, `matchPreset`, `restoreRange`); presets count back from the newest day with data (`/api/span`), inclusive, clamped to the first day. The URL always holds explicit `from`/`to`; which preset is highlighted is derived by matching, so there is no separate preset state to drift. The last choice is stored in `localStorage` (`cx5.range`: a preset id, `all` or `custom`) and `useRestoreSavedRange` (in `range.ts`, called from `App`) re-applies a saved preset once per page load, only when the address has no period. The bar uses native radio inputs for keyboard support.

## Trends (monthly comparison)

`backend/src/mazda_dash/api/trends.py` builds one row per calendar month in the period (`GET /api/trends/monthly`), from the events inside the period, with `days_covered` / `partial`; months without data stay in the series with `None` metrics (a gap, not 0). Distance is odometer-based (it matches `km_in_range`), consumption comes from trip segments, and "new faults" excludes anything first reported on the first diagnostic day. `tests/test_trends.py` pins these (including the gap and partial-month cases). All comparison logic lives in `frontend/src/trends.ts` (`METRICS` definitions with polarity, `metricValue`, `compare`, `describeChange`) and is unit tested; `pages/Trends.tsx` only renders. To add a metric: add the field to `MonthMetrics` and `monthly_metrics`, add a `MetricDef` (set `additive` for totals so "per day" works, `polarity` for the green/red colouring, `money` for an amount), give it an entry in `COMPARABILITY` (`compare.ts`: a test fails without one) and, if it cannot be added up from months, in `PERIOD_UNAVAILABLE`, extend the tests, and raise `SUMMARY_VERSION` (phone) because the monthly answer changed. The cost figures (M33) are in this answer too.

## Several diagnostic reports (M10)

A report's id is a hash of the dump's content, so different dumps (even same date and VIN) are separate reports and an identical copy under another file name is skipped. `GET /api/diag/history` returns one headline row per report (oldest first) for the history table and charts (`components/ReportHistory.tsx`). The Diagnostics page keeps its selection in the URL (`?report=` and `?compare=`, via `pickReport` in `lib.ts`; an unknown id falls back to the newest report with a notice) and always orders a comparison from the earlier to the later report. `sample.py` writes three visits (`DIAG_VISITS`); changing them means updating `tests/test_diag_reports.py` and `tests/test_sample.py`.

## Offline phone app (`mobile/`)

`PLAN.md` ("Standalone offline app for iPhone") has the design and the measurements behind it. `backend/src/mazda_dash/pack.py` exports the database as a `.cx5pack` (Parquet tables + manifest; GPS positions excluded; `--reference` adds per-view fingerprints used by tests). `mobile/` loads it into DuckDB-WASM in the browser, rebuilds every view from `views.sql`, and answers the pages' `/api/...` requests with a TypeScript port of the API. `*.cx5pack` files contain a VIN: they are gitignored and must never be served on the network or deployed (only `mobile/public/demo-cx5.cx5pack` and `demo-cx60.cx5pack`, built from the synthetic data, are). The Mac app (`frontend/`, `backend/`) is the reference and works without `mobile/`.

M13 added `mobile/src/engine/`, the Python API re-implemented in TypeScript on DuckDB-WASM. **Any change to an endpoint, its SQL, its response model or `views.sql` in `backend/` must be mirrored there** (`api.ts` routes, the handler files, `shapes.ts` for model fields), then checked with `make mobile-test`: it records what the Python API answers on the sample data (`make mobile-golden` → `mobile/contract/`, gitignored) and replays it on the TypeScript engine; `make mobile-golden-real` does the same on your own database (delete `mobile/contract/real` afterwards, it holds your VIN). Give every `ORDER BY` a tie-breaker. The pack keeps whole every signal source except `rts`; `views.sql` may name `rts` signals only as `signal = '<name>'` (or a family with `starts_with`, see M20).

M14 added the app itself in `mobile/src`: `main.tsx` wires `DataController` (`controller.ts`, UI-free: engine start, the stored packs, import/switch/delete, acks replay), IndexedDB `storage.ts`, `engine-browser.ts` (DuckDB-WASM in a worker, queries run one at a time) and `App.tsx` (bottom tab bar) around the pages of `frontend/src` (alias `@frontend`). The hooks reach the API only through `frontend/src/api/client.ts`; the phone replaces its `fetch` with `setFetch(createFetch(api))`, so **frontend code must keep using that client and never call `fetch` for `/api` directly**, and must not load anything from another host (the phone app promises no outside request; fonts are bundled). `make mobile-dev` / `mobile-build` / `mobile-test`.

M15: `vite.config.ts` generates `dist/sw.js` from `sw.template.js` (precache list + content-hash version; never edit `dist/`); `src/pwa.ts` registers it in production builds only and drives the update prompt; `controller.ts` also asks for persistent storage and remembers (`localMemory`) that data existed, to tell evicted data from a first run. Shared CSS changes for phones live in `frontend/src/index.css` under `max-width: 640px` / `pointer: coarse` queries and must leave desktop widths unchanged; `DateRangeBar` has a narrow-screen toggle. A new file the app loads at run time must come from the build output (or `mobile/public/`), otherwise the service worker will not cache it and the app breaks offline. The iOS Simulator reaches `localhost`, so `make mobile-build` + `npm run preview` there tests install and offline (stop the server and reload).

**Keep both implementations in step (M16).** Adding or changing an API route, its SQL, its response model, `views.sql`, or what the pack exports means changing the Python API, the TypeScript engine (`mobile/src/engine/`: route in `api.ts`, handler, `shapes.ts`) and, if needed, the golden matrix in `backend/src/mazda_dash/contract.py`, in one change; `make mobile-test` must pass (CI runs it in the `mobile` job, and a Python test fails when a route has no golden case). Hosting: `.github/workflows/pages.yml` publishes `mobile/dist` (app + synthetic demo pack only) to GitHub Pages after `make mobile-test`; both it and CI fail if `dist` holds any `.cx5pack` other than the two `demo-*.cx5pack`, and `make audit` fails on any non-ignored `*.cx5pack`. Never commit or deploy a real pack.

**Several models on the phone (M26).** A pack holds one car model and says which in its manifest (`model: {id, name, platform, hidden_pages}`; `PACK_FORMAT` and `SUPPORTED_FORMAT` are 2, an older pack is refused with the "older version" message). The phone stores one pack per model (IndexedDB v2: stores `packs` keyed by model id and `acks` keyed `<model>:<dedup_key>`; a pack of the first version is found in the old `pack` store, discarded and reported once). `DataController` (UI-free, tested in `test/controller.test.ts`) keeps the stored packs, loads **one model into the engine at a time** and exposes `packs`, `current`, `switchTo(id)`, `importPack` (replaces that model's pack; shows it only when it replaces the model on screen or none is loaded, otherwise just stores it, so the address and the data on screen cannot disagree), `loadDemo` (imports both demo packs, `demo-cx5` and `demo-cx60`), `deleteModel`, `deleteAll`. The engine `Api` answers `GET /api/models` from the stored packs (the loaded one is `default`) and **refuses a request that names another model with the same 404 text as the Python API**, so the shared hooks, which now put `model` in every request and key, can never be answered from the wrong pack. The address decides: `MobileApp` follows `?model=` (hash router: `#/?model=cx60`) by calling `switchTo`, the shared `ModelSwitcher` / `ModelGate` / `useSwitchModel` do the rest, and a model's `hidden_pages` hide tabs and redirect. The contract goldens are one folder per sample model (`mobile/contract/<model>/`, `make mobile-golden` records every model, `contract.generate_all`; `CONTRACT_DIR=contract/real` still replays one folder), and a Python test fails when a model with sample data has none. `loadPack` gives every Parquet file a name of its own per load: DuckDB remembers a file's metadata by name, so a second pack (another car, or simply a newer export) under the same name failed with "No magic bytes". The controller loads a **copy** of the stored bytes each time (the engine takes the buffers it is given). Hosting and CI now expect `demo-cx5.cx5pack` and `demo-cx60.cx5pack` in `dist` and nothing else with that extension.

Appearance (Auto / Dark / Light): `frontend/src/theme.ts` (choice in `localStorage` `cx5.theme`, applied as `data-theme` on `<html>`; both `index.html` files apply it before first paint and carry two `theme-color` metas) with `components/ThemeToggle.tsx` (segmented control in the Mac rail, `ThemeCycleButton` as the last cell of the phone tab bar). In `index.css` the light palette exists twice (device in light mode and not forced dark, and forced light) because CSS cannot share one block across a media query and an attribute selector; `theme.test.ts` fails if they differ. Add a new colour variable to the dark block and BOTH light blocks. Use `var(--...)` for colours, never literals, so both themes work.

Settings (`config/models/<id>/settings.yaml`: `car_timezone`, `tire_stale_hours` and the optional fuel price, see below) are loaded by `model/settings.py` into `ref_settings`; views read them (`v_tire_snapshots`), the pack carries the table, and the phone app has no copy of the values. Time zone conversion lives in SQL (ICU) so Python and the phone cannot disagree: use one `make_timestamp(epoch_us(timezone(zone, ts)))`, never nested `timezone(...)` calls (the in-browser DuckDB cannot run them), and do not depend on the session TimeZone. `tire` views use the column name `reading_at` because `at` is reserved. Hard time cases (clock changes, impossible dates) are added to the golden database in `contract.py` (`TIRE_CLOCK_EDGE_CASES`), not to the sample files. `make timezone` checks the configured zone.

**Fuel cost (M33).** `fuel_currency` plus `fuel_prices` (a dated list) or `fuel_price_per_l` in `settings.yaml` are validated in `model/settings.py` and stored in `ref_settings` and `ref_fuel_prices`, which the pack carries (an older pack lacking the table is refused). The view `v_fuel_prices` gives each price its span and the earliest also applies before its date. **Cost = the litres of each trip times the price in force on its day**: `cost_per_100km` and `fuel_cost_est` on `MonthMetrics`, `cost_per_100km_in_range` and `currency` on the Overview, computed with the same `PRICED` join in Python and TypeScript, never without a configured price and never shown as what was paid. The repository's `config/models/*/settings.yaml` hold the author's own prices. The demo and the goldens ingest with the settings file the sample generator writes next to each model's sample data (`sample_data/<id>/settings.yaml`: time zone and price from the `Profile`), so they never touch the real settings; `ingest --settings` and `ingest(..., settings_path)` take it (a test must never assume the real settings have no price). A new money metric uses `¤` in its unit and `money: true`, and a currency must match to compare two cars.

Warning-lamp flags (M20): the 128 `vdt_*` columns are read as a signal *family* with `starts_with(signal, 'vdt_2_warningpt_')`; `pack.py` finds such prefixes (`used_signal_prefixes`) and exports only family members with more than one value (`varying_in_families`, which must stay identical to the `varying` test in `v_warning_flag_readings`: a view that listed constants would differ in the pack). Do not write signal lists as `signal IN (...)` or `LIKE` in `views.sql` (a test forbids it); use `signal = '<name>'` for single signals and `starts_with` for families, and the phone refuses packs lacking a family. Hints are shown as hints: never present a co-occurrence as the meaning of a flag, and never invent titles in `config/models/<id>/codes/warning_flags.yaml`.
