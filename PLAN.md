# Mazda CX-5 Data Dashboard — Plan and status

Personal dashboard to analyse the data Mazda exported for my CX-5, with alerts for relevant events. The files in `data/` are described in [docs/data-dictionary.md](docs/data-dictionary.md); how to use the app is in [README.md](README.md); [CLAUDE.md](CLAUDE.md) is the tour of the code. The repo is meant to be open-sourced, so privacy and reproducibility were designed in from the start.

**Status: complete. All planned milestones (M1–M27) are done** (M21–M27: several car models; M28, adapting to a real CX-60 export, is conditional and not started): the Mac dashboard (M1–M11), the offline iPhone app (M12–M16, live on GitHub Pages and tested on a real iPhone) and four features built from the car's own signals (M17 next oil change, M18 the car's own warnings, M19 tire reading time, M20 warning-lamp flags). What is left is under "Ideas not built". This file keeps the design decisions and the plan each milestone was built from, with an "as built" note where the result differs; it is a design log, so some sections describe the plan in the future tense before the "as built" note that follows them. **Planned next, not started: comparing models and periods and the estimated fuel cost (M29–M33), see "Comparing models and periods".**

## Decisions

| Topic | Choice | Why |
|---|---|---|
| Python tooling | `uv` + `Makefile` | Preference; reproducible with `uv.lock` |
| Storage | **DuckDB** (single file) | Columnar and analytical; reads the wide `dtc-ssr` CSV and mixed timestamps well; `read_csv` makes re-ingestion trivial. SQLite would work but is clumsier for this kind of analytics |
| API | **FastAPI** | Thin read-only layer over DuckDB (plus acknowledging alerts); typed responses; OpenAPI schema generates the frontend types |
| Frontend | **React + Vite + TypeScript** | Flexible for alerts, drill-downs and a polished UI; Streamlit is faster to start but limiting for a long-lived, shareable project |
| Charts / tables | Recharts / a small sortable `DataTable` component | Chosen in M4; TanStack Table v9 was skipped (new API, not needed) |
| Tests | pytest (backend), Vitest (frontend) | |
| Time | All timestamps stored as naive UTC; periods are inclusive UTC days | One convention end to end; the browser shows local time |
| Alerts | Rules in YAML, each alert raised once per `dedup_key` | Acknowledging is a workflow; rules are tunable without code |
| Period filter | `from` / `to` in the URL and the API | Bookmarkable; state (active faults, alerts, diagnostic report) is deliberately not filtered |

## Privacy / open-source rules

- `data/` (every model's folder), `db/`, `*.duckdb`, `*.cx5pack` (phone data packs: they hold the VIN) and `.env` are gitignored. The VIN and personal data never get committed.
- `sample_data/<model>/` holds **synthetic** data in the same format (generated by `make sample-data`), so others can run the app; `make audit` fails if it ever holds a VIN other than the synthetic ones.
- Mazda-specific code descriptions live in editable files (`config/models/<id>/codes/*.yaml`, per model, never shared); only publish codes whose meaning is public or user-supplied.
- MIT licence and README are in place (M7). Before publishing, run `make audit`: it looks for the VINs and positions found in `data/` in every publishable file and in the whole git history, and lists commit author emails.

### M8 — Date-range filter (from / to) ✅ done
- **Backend:** one shared `date_range` dependency (`from`, `to`; inclusive days, UTC; `from <= to` else 422) applied in SQL to the time-based endpoints: odometer, fuel, trips, status timeline, doors, warnings (frequency, daily, events), fault events and read-outs, overview figures. Without parameters nothing changes (all time).
- **Not filtered (state, not events):** faults active in the latest read-out, the alerts list, and the diagnostic-tool report (it has its own picker, M10).
- **Frontend:** a date-range bar with two date inputs; the range lives in the URL (`?from=2026-06-12&to=2026-07-12`) and every query key includes it. Overview tiles describe the chosen range.
- **Edge cases:** an empty range shows a clear message; the range survives navigation between pages.
- *As built:* `GET /api/span` bounds the date pickers; `fuel/monthly`, `warnings/frequency` and `dtcs/frequency` re-aggregate inside the endpoint to honour the range (they mirror the corresponding views).

### M9 — Quick ranges (presets) ✅ done
- Presets: **Last week**, **Last 2 weeks**, **Last 30 days**, **Last 60 days**, **Last 90 days**, **All time**. The active preset is highlighted; editing a date manually clears the highlight (custom range).
- **Decision (confirmed):** presets count back from the **most recent data point**, not from today. Exports are snapshots, so "last 30 days" relative to today would be empty after a few weeks without a new export. The bar shows the resolved dates.
- The last preset is remembered in the browser (default for new visitors is All time; a link with dates wins). Keyboard accessible (a native radio group), works on phone width.
- Pure date logic (`resolvePreset`, `matchPreset`, `restoreRange`) lives in `lib.ts` with unit tests, including month ends and datasets shorter than the preset.

### M10 — Choose any diagnostic-tool report ✅ done
- The report selector is **always visible** and lists each report as "date · odometer · file", newest first, with the selection in the URL (`?report=`; `?compare=` for the comparison).
- A **report history** panel: lifetime km, lifetime l/100 km, ignition cycles, engine hours, monitors passed and faults listed per report, with small charts when there are 2+ reports. The "compare with" table stays and always reads from the earlier report to the later one.
- Ingest: several `*diag-tool*.txt` files (even with the same date or VIN) load as separate reports; an identical copy under another name is skipped; re-running adds nothing.
- `sample.py` writes **three** diagnostic reports (as if downloaded at three different dates); tests cover the report list, history, switching and comparison across dates.
- *As built:* `GET /api/diag/history`. With real data there is one dump today; further dumps appear once their `.txt` files are in `data/` and `make ingest` is run.

### M11 — Monthly comparison page ("Trends") ✅ done
A page showing how each metric evolved month by month, with the change against the previous month.
- **Presentation:** a card per metric with a bar chart across all months (latest highlighted), the current value, and "x % more / less than May" with an arrow. Colour reflects whether the change is good or bad for that metric (less fuel use is green; more warnings is red; distance driven is neutral). A table view (months as columns, change underneath) for exact numbers.
- **Incomplete months:** the first and last month are usually partial, so they are marked "partial" and totals can be shown **per day covered** via a toggle. Months without data show a gap, not zero; a missing previous month shows "no previous month".
- **Backend:** `GET /api/trends/monthly` returns one row per calendar month in the selected period (including days covered); the change and its good/bad direction are computed in the frontend (unit-tested).
- *As built, and where it differs from the plan:*
  - Monthly figures are computed in `api/trends.py` instead of a `v_monthly_metrics` view, so the date range applies *before* aggregation (a month cut by the period only counts its days inside it and is reported as partial).
  - *Alerts raised* is not a metric: alerts are only evaluated for the last `lookback_days` each time you run `make ingest`, so older months would always show 0.
  - *Trips* became two metrics, **Drives recorded** (stretches between status snapshots) and **Days driven**, because the car's snapshots are not true trips. *Distance* comes from the odometer, not from summed stretches (which cover only part of it); *fuel used* is estimated as distance × consumption.
  - *New faults* excludes faults first reported on the first day of diagnostic data, which may have existed long before the data begins.

## Standalone offline app for iPhone (M12–M16, built)

**Goal.** Use the dashboard on an iPhone (iOS 27 is the target), with the data on the phone, **without the Mac being on or reachable**. **Hard constraint:** the current app must keep working exactly as today (`make dev` → `http://localhost:5173`, `make demo`, all tests). The new app therefore lives in its own folder, **`mobile/`**, with its own `package.json`, build and tests. The existing `backend/` and `frontend/` get only the small, tested changes listed under "What changes in existing code".

### How it works

```
 on the Mac (unchanged)                      on the iPhone (new, offline)
 data/ ─ make ingest ─▶ db/mazda.duckdb      ┌──────────────────────────────────────────────┐
                           │                 │ installed web app (static files, cached)     │
              make mobile-pack (new)         │   same screens as today (reused from         │
                           ▼                 │   frontend/src)                              │
                 db/mazda.cx5pack ──AirDrop / Files / iCloud Drive──▶ "Import data"        │
                 (zip of Parquet + manifest) │   DuckDB-WASM + TypeScript "API" ◀── IndexedDB│
                                             └──────────────────────────────────────────────┘
```

- **A data pack.** `make mobile-pack` (new, in `backend/`) exports the database tables to **Parquet** files plus a `manifest.json` (pack format version, creation time, row counts, newest data day) in one zip, `db/mazda.cx5pack` (gitignored). Parquet, not the `.duckdb` file, because the browser's DuckDB is a different, independently versioned build than this project's (backend: DuckDB 2.0.0; `@duckdb/duckdb-wasm` is numbered 1.33.x), and the `.duckdb` storage format is not guaranteed to open across versions, while Parquet is.
- **The same SQL.** The app loads the Parquet tables into DuckDB-WASM and runs the existing `backend/src/mazda_dash/model/views.sql` unchanged (imported from the backend folder at build time, so there is one source of truth). Code descriptions need no YAML parsing: the `ref_*` tables travel inside the pack.
- **The same screens.** The standalone app reuses the existing React pages and components from `frontend/src` through a Vite alias. Only the data layer is swapped: the pages talk to `/api/...` through one `openapi-fetch` client, and in the standalone app that client's `fetch` is replaced by an in-browser implementation of the same routes (28 when this was planned, 33 by M20). So the screens, types and URL parameters (`?from=`, `?report=`) are identical.
- **Alerts.** Alert rules run on the Mac during `make ingest`; the pack carries the resulting `alerts` table. Acknowledging an alert on the phone is stored on the phone (IndexedDB) and layered over the pack's alerts. The phone does not evaluate rules (that would mean porting the alert engine; not in scope).
- **Installing without a Mac.** An iPhone can only install an offline web app (service worker) from an **HTTPS** address, not from a Mac on the local network. The plan is to host the **static build, code only**, on GitHub Pages (or any static host). The site never receives any data: the pack is imported from the phone's own storage and never leaves it. The site also offers "Load demo data" so anyone can try it.
- **Updating the data.** On the Mac: ingest a new Mazda export as today, run `make mobile-pack`, send the pack to the phone, tap **Import data**. Importing replaces the previous pack on the phone (acknowledgements are kept).

### What changes in existing code (the only seams)

1. `frontend/src/api/hooks.ts`: the `createClient(...)` call moves into `frontend/src/api/client.ts` so the standalone build can substitute its own client. No behaviour change; covered by the existing typecheck, lint, tests and build.
2. `backend/`: **new** files only (`pack.py`, tests, a `make mobile-pack` target). Nothing existing is modified except the Makefile gaining targets.
3. CI: new jobs for `mobile/`; the existing jobs stay as they are.
4. Responsive fixes in `frontend/src` (see "Phone layout audit" below): CSS under narrow-width media queries plus a few layout tweaks, so the Mac app also behaves on a narrow window. Desktop widths must look unchanged (checked with before/after screenshots).

**Finding after the real iPhone, rounds 1 and 2: even on a phone that runs code 60–70× slower than the Mac (see the processor row; probably JIT off), the trimmed pack gives a working database in roughly 1.5–2.5 s once the engine is cached, and each query takes tens of milliseconds, so a screen shows in well under a second.** Cheapest fix already made: `signal_readings` held 200 signals of which the views read 24 (4,546 of 41,680 rows), so packs are now trimmed to those by default (`--all-signals` restores everything). On the Mac this makes table loading about 7× faster (128 ms to 18 ms), views 3× and the typical page's queries 3.5×, with identical view results (tested); compression (zstd, snappy, none) makes no measurable difference, so zstd stays. DuckDB's browser OPFS persistence was tried (so the tables would not be rebuilt at each launch) and **did not persist** in this version (the file stayed empty, DuckDB logged "buffering"), so it is dropped; an alternative is saving the database file's bytes in IndexedDB if loading is still too slow after trimming.

**Decision gate: GO.** The risks that could have stopped the plan did not materialise: the SQL needs no changes, results are identical in Chrome, desktop Safari, **iOS Safari 27** and on a **real iPhone**. Speed, the only open question, is answered: round 1 (full pack, first download of the engine) took 9.3 s; round 2 (trimmed pack, engine cached) is about 1.5–2.5 s even on this slow phone. The first install still downloads the engine once (7.7 MB gzip, 5.2 MB brotli on a host that compresses; the Mac's test server did not compress, which is why round 1 looked so bad). M12 is **closed with a final GO**. The fallbacks in the milestone text are not needed.

**What this changes in the later milestones:**
- Ship the **trimmed** pack by default (done in M12); keep the app shell responsive while the engine starts (show the screen skeleton and a progress line at once; start the engine and load the data in the background).
- Ship only the modern (EH) engine build; cache it with the service worker (about 8 MB over the network once, about 36 MB of storage on the device).
- `crypto.subtle` is disabled on plain `http://` addresses other than localhost, so the app must not depend on it (HTTPS hosting on GitHub Pages is fine, local-network tests are not).
- Beware ties in `ORDER BY` (equal sort keys may come out in a different order in a different engine): the M13 contract tests must compare with deterministic orders, and the SQL should gain tie-breakers where needed (one was already fixed in the API).
- The pack carries `views_sql_sha256`; the app should refuse or warn about a pack made for a different `views.sql`.

#### M13 — Standalone data engine (TypeScript)
Re-implement the API inside the browser with **identical JSON**.

### Limits (by design)
- **Read-only viewer.** New Mazda exports still go through `make ingest` on the Mac, then a new pack to the phone. Parsing Mazda's zip/CSV files on the phone would mean porting the ingestion code; not planned.
- Alerts are not re-evaluated on the phone.
- Two implementations of the API must be kept equal; the golden tests make drift visible but cost maintenance.
- iOS decides how long web-app storage survives; keep the pack file (iCloud Drive or Files) as the source of truth.

### Risks and how the plan handles them

| Risk | Handling |
|---|---|
| DuckDB-WASM too slow or too big on an iPhone | measured first, in M12, with a written go/no-go and fallbacks |
| SQL differences between DuckDB 2.0.0 and the WASM engine | run all of `views.sql` in M12; adapt the SQL only if needed, keeping Python and WASM results identical |
| The TypeScript API drifting from the Python one | golden contract tests (M13), regenerated and diffed in CI |
| iOS evicting stored data | persistence request, detection and one-tap re-import (M15); the pack file is the backup |
| Phone with the JIT compiler off (Lockdown Mode or similar): code runs 10–70× slower | measured: still ready in about 2 s and queries in tens of ms; the app shows its screen skeleton immediately, and the README explains how to exclude the site from Lockdown Mode for full speed |
| Stale cached app after an update | versioned precache and an update prompt (M15) |
| Privacy of hosting | the host only ever serves static code; CSP `connect-src 'self'`; verified by blocking the network (M15, M16) |
| Breaking the Mac app | separate folder; only the one-line client seam in `frontend/`; both apps run in CI |

### Decisions

1. **Folder name: `mobile/`.** Confirmed.
2. **Host the app's code on GitHub Pages** (public, code only; no data ever in the repo or the site). Confirmed.
3. **Move the data pack by AirDrop / Files / iCloud Drive.** Confirmed.
4. **Read-only viewer, alerts computed on the Mac.** Confirmed. What this means: the phone gets a snapshot of the database that the Mac made, including the alerts the Mac had already raised. On the phone you can read everything, change the period, compare months, and acknowledge alerts. You cannot (a) drop a new Mazda zip onto the phone and have it processed, (b) make the phone raise new alerts or change the alert thresholds. For both you go through the Mac (`make ingest`, then a new pack). One consequence: an alert you acknowledge on the phone is remembered on the phone only; the Mac does not know, and the other way round. The alternative is to port the ingestion code and the alert engine to the phone as well (roughly two or three more milestones), so the phone would be fully independent of the Mac. Not recommended for now; it can be added later without redoing the rest.
5. **Real iPhone testing:** yes, iOS 27, in addition to the iOS Simulator, in M12 and M15. Confirmed.

Must handle the clock change in late October and invalid parts (`255`, `0` year).
- **View and API:** `v_tire_readings` with `measured_at` (UTC), the snapshot time, and the age of the measurement at snapshot time; consecutive snapshots that repeat the same measurement are one reading.
- **UI:** the tire panels say "measured 18:02, 41 min before this snapshot"; the Status tire chart uses the measurement time on its axis (fewer duplicate points); stale readings (older than a configurable number of hours) are marked.
- **Alerts:** `low_tire_pressure` keys on the measurement time instead of the snapshot time, so one low reading counted in several snapshots raises one alert.
- **Done when:** both implementations convert times identically (DST edge cases in the goldens) and the demo data has readings whose measurement is older than the snapshot.

**M19 as built.**
- **Settings file** `config/settings.yaml` (`car_timezone`, `tire_stale_hours`), loaded into a `ref_settings` table by `build_model` (unknown settings, an invalid time zone name or a stale limit of 0 are errors; defaults UTC and 6 h when the file is missing). The table is in the data pack (`TABLES`), so the phone reads the same values; the phone app refuses an older pack without it with a clear message. `make timezone` (`timezone_check.py`) tells whether the configured zone fits the data and groups the zones that do by the clock offset they imply (it cannot tell apart zones that behaved alike during your data, so it says to choose the one where you live).
- **Views** (`views.sql`): `v_tire_snapshots` (per status snapshot: `measured_at` in UTC, `age_minutes`, `stale`) and `v_tire_readings` (one row per distinct measurement; repeats are folded, with first and last age and the number of snapshots; a snapshot with no valid time is its own reading with `time_known = false`). **The conversion is a single `make_timestamp(epoch_us(timezone(zone, local_time)))`** because the in-browser DuckDB crashes or cannot bind `timezone()` calls nested in each other; Python and the browser agree on every case tested.
- **API:** `GET /api/status/tires` (period-aware, by measurement time) and three new fields on the Overview `status` (`tire_measured_at`, `tire_age_minutes`, `tire_stale`).
- **Alert:** `low_tire_pressure` now keys on the measurement time (`v_tire_readings`), so a low reading repeated in several snapshots is one alert dated when it was measured. Snapshots without a time behave as before.
- **UI:** the Overview tire panel says "measured 30 Jun, 18:56, 5 min before this snapshot" (amber "old" when stale); the Status tire chart plots one point per measurement at the time it was taken with a note counting stale and unknown-time readings. Wording is in `fmtAge` / `tireMeasuredNote` / `tireReadingsNote` (tested).
- **Phone:** `tireReadings` in the TypeScript engine, the extended status, and goldens. **DST edge cases are in the goldens**: `contract.py` adds 17 clock readings to the temporary database it records from (the forward and back clock changes of Lisbon on 2026-03-29 and 2026-10-25, a leap day, impossible dates, 255 and year 0), never to the sample files, and the browser engine reproduces every one (also on the author's real data).
- **Sample data:** the demo car measures 2–41 minutes before each drive ends, so its clock runs through the March clock change; snapshots taken after the car stood still for hours show old measurements (9 stale, one of 62 hours), nine repeats are folded, and one snapshot has no valid time. Added without changing the random stream (only the status CSV differs); `tzdata` was added as a backend dependency so the zone database is the same everywhere.
- **Real data (author's export):** with `Europe/Lisbon` the measurement times fit perfectly (196 snapshots, none in the future, median 12 minutes old, oldest 26 hours, 6 snapshots stale, 185 distinct measurements). Run `make model` once to get the settings table and the views.
- Pitfall found on the way: `at` is a reserved word in DuckDB (the column is `reading_at`).

### M20 — Warning-lamp flags (the 128 bit flags)
- **View and API:** `v_warning_flags`: per flag, readings set, share of readings, first and last seen, and the timeline of when it was on; only flags that ever change are listed by default. `GET /api/status/warning-flags`.
- **Labels:** user-supplied meanings in `config/codes/warning_flags.yaml` (like `warnings.yaml`: title, severity, notes); unmapped flags appear in `make unmapped` and the dashboard's unmapped list.
- **Decoding aid:** for each flag that changes, show which `$` warning codes and which diagnostic faults appear around the times it is on (for example "set in 94 snapshots; `$…` codes co-occur in N of them"), clearly marked as a *hint*, not a fact. This is research support for filling in `warnings.yaml` and the flag labels.
- **UI:** a "Warning lamps" panel on Status with the timeline; flags set on the day of a diagnostic report are called out.
- **Alert rule** `new_warning_flag`: a flag that has never been set before is set for the first time (like `new_warning_code`).
- **Done when:** the panel, hints, labels and alert work on sample and real data, with identical results in both implementations.

**M20 as built.**
- **Views** (`views.sql`): `v_warning_flag_readings` (every valid reading of the 128 flags, **only for flags that take more than one value**), `v_warning_flag_episodes` (runs of consecutive readings with a flag on; `ongoing`) and `v_warning_flags` (per flag: readings, readings on, share, first/last on, on now, your title/severity/notes, whether it was first set on a diagnostic-report day, number of runs). `v_unmapped_codes` gained kind `warning flag`, so `make unmapped` and the Overview's "N codes have no description yet" include flags without a meaning.
- **Labels:** `config/codes/warning_flags.yaml` (title, severity, category, notes, like `warnings.yaml`; ships empty with a clearly marked made-up example, never guesses) loaded into `ref_warning_flags` by `lookups.py`.
- **API:** `GET /api/status/warning-flags` (flags in power-train-then-body order, every run, the time span of the readings; a state endpoint) and `GET /api/status/warning-flags/hints?flag=&window_hours=` (404 for a flag that does not change). **Hints:** for each warning code and each fault, in how many readings with the flag on / off it appears within the window (default 2 h, up to 48), as a share of the readings with it on / off; only things more common when the flag is on are listed, ranked by that difference (at most 8 each). One request takes about 30 ms on the real data. Presented as "a hint, not a meaning". On the author's data one flag (`vdt_7_warningbody_2_44`, set 3 times) is on exactly when warning `$1B4` is near (100% of its readings against under 1% otherwise): the kind of lead this is for.
- **Alert `new_warning_flag`** (default info; severity comes from your yaml once you describe the flag; `ignore_flags` with names checked against the `vdt_2_warningpt_N_N` / `vdt_7_warningbody_N_N` pattern): a flag first set inside the lookback window, one alert per flag, mentioning when it is a diagnostic-report day and, without a meaning yet, where to look and where to describe it. On the author's data the two power-train flags first set on 15 Oct will raise one alert each on the first run.
- **UI:** a "Warning lamps" panel on Status: one row per changing flag (your title or "Power train flag 23", the car's name, badges *on now* / *first set on a report day* / *no meaning yet*, a timeline bar across the data, "on in 94 of 214 readings"), opening a row shows its details and the hints with a 0.5 / 2 / 6 / 24 h window selector. Wording and timeline maths are `lampLabel` / `lampBars` / `fmtShares` (tested).
- **Phone pack:** the pack scans `views.sql` for signal *families* written `starts_with(signal, '<prefix>')` (`signal_prefixes` in the manifest) and exports only the family members that vary, so 128 flags cost 4 flags' rows (27,392 → about 800 rows on the real data; the real pack is 468 KiB, smaller than before). `ref_warning_flags` joined `TABLES`; the phone app refuses an older pack that lacks the table or the families. The browser engine reproduces Python on every golden, including hints for each flag at several windows and the 404 / 422 cases, and on the real data.
- **Sample data:** six flags as plain columns like the real file: two that never change (and so never appear), one on in the mornings, two set only on diagnostic-report days, one that first appears in the last days (raising the new-flag alert). Derived from the clock only, no random numbers.
- **Real data (author's export):** 4 flags change (`vdt_7_warningbody_1_30` on in 94 of 214 readings and 52 runs, `vdt_7_warningbody_2_44` 3, `vdt_2_warningpt_1_23` and `vdt_2_warningpt_2_46` 4 each, the last two first set on the day of the diagnostic report); none has a meaning yet. Run `make model` once.
- Pitfall found on the way: a view that lists constant flags makes the pack's copy (without them) differ in the view fingerprints; the readings view itself is therefore limited to changing flags, which makes the Mac database and the pack agree by construction.

### Decisions (all confirmed)
1. **Order:** M17 oil, M18 car warnings, M19 tire time, M20 lamp flags (easiest and most useful first). Confirmed.
2. **Time zone (M19):** a setting in a small config file, with a suggestion from the data (not the browser's time zone, which would be wrong when travelling). Confirmed.
3. **Default thresholds:** oil change due below 1,000 km; tire data "stale" after 6 hours; car warning flags severity `warning`. Confirmed.
4. **Phone app:** all four ship to it in the same milestone (the engine and golden tests are extended each time), not as a separate catch-up. Confirmed.

## Several car models (M21–M27, built; M28 conditional)

**Goal.** Support more than the CX-5 (first target: the CX-60) in the whole app, not only in ingestion: each model has its own raw exports in its own folder, its own database and configuration, and the dashboard (Mac and phone) lets the user choose which model to look at. **Hard constraints:** a CX-5-only install keeps working, with no visible model chrome beyond a label; nothing from one model leaks into another (data, alerts, code descriptions); the privacy rules (no VIN committed, no real pack deployed) apply to every model.

### What the code looks like today (why this is mostly plumbing)
- Ingestion is already model-agnostic: files are found by the `_<kind>-` part of the name (`*_war-*.csv`, …), so the platform code in the name (`24pf`) is not used. The `rts`/`vis`/`alt` signals are stored in long form and views read them by `signal = '<name>'`, so a signal that a model lacks is simply an empty reading, not an error.
- What is single-car by construction: one `data/` folder, one `db/mazda.duckdb`, one `config/` (code descriptions, alert rules and `car_timezone` all describe *the* car), `MAZDA_DB` read by `api/db.py`, no model in the frontend's query keys or URLs, and one pack in the phone app's storage.

### Decisions (confirmed)
| Topic | Choice | Why |
|---|---|---|
| Storage | **One DuckDB file per model** (`db/<model>.duckdb`), not one shared database with a `model` column | `views.sql`, the alerts engine, the pack, the TypeScript engine and every golden test stay as they are; a model cannot leak into another; deleting or resetting one model is one file. A shared database would mean a model column in every table, view, key and `dedup_key` |
| Model id | A short slug: `cx5`, `cx60` (lower case, `[a-z0-9]+`); the display name and platform code live in `model.yaml` | Used in folder names, URLs, file names and the API |
| Raw data | `data/<model>/` (e.g. `data/cx5/`, `data/cx60/`), same file kinds as today | What was asked for. Existing flat `data/` keeps working as the `cx5` folder during migration (see M21) |
| Configuration | `config/models/<model>/` with `model.yaml`, `settings.yaml`, `alerts.yaml`, `codes/*.yaml`; a missing `alerts.yaml` or `settings.yaml` falls back to a shared `config/defaults/` (never the code descriptions) | Warning codes (`$182`), DTC meanings and flag labels can differ per platform, so descriptions must not be shared; alert thresholds and time zone usually differ per car |
| API | Every route takes `model` (query parameter, default = the only model, or the first in `models.yaml` order); `GET /api/models` lists them | Same pattern as `date_range`; one FastAPI app serves all models, one short-lived read-only connection per request on the chosen file |
| Frontend | The model is part of the URL (`?model=cx60`) and of every query key, carried by the same link helpers as the date range; the last choice is remembered in `localStorage` (`cx5.model`) | Bookmarkable; no stale data from another model; same mechanism as the range, so it is already proven |
| Phone | One pack per model, several packs stored on the device, a model switcher in the app | A pack is already one database; the engine is untouched |
| Model-specific features | Out of scope at first: pages show whatever the model's data has; a model can hide a page with `pages:` in `model.yaml` | A plug-in hybrid (CX-60 PHEV battery and charging signals) needs a real export to design; see M28 |

### M22 — Per-model ingest, configuration and alerts ✅ done
- **Ingest:** `ingest(model)` reads `data/<id>/` into `db/<id>.duckdb` and builds the model with that model's config; the CLI takes `--model` (default: all). A model folder with no recognisable files is reported, not silently skipped. The VIN-per-file check warns when one model's folder contains two different VINs (the plan assumes one car per model; see "Open questions").
- **Config per model:** `build_model` takes the model's `config/models/<id>/` (codes, `settings.yaml` with its own `car_timezone` and `tire_stale_hours`); `alerts.yaml` is read per model with a fallback to `config/defaults/alerts.yaml`. `make unmapped` and `make timezone` take the model. Code descriptions never fall back to another model: an unmapped code stays "unmapped" (CLAUDE.md rule: never invent titles).
- **Compatibility report (`make compat MODEL=cx60`):** compares what `views.sql` reads (signals as `signal = '…'`, `starts_with` families, ECU and warning kinds) with what the model's database contains, and lists the signals the views want but the model lacks and the signals the model has that nothing reads yet. This is how a new model is brought up without guessing, and it is the input for M28.
- **Alerts:** the engine runs per model database; `dedup_key` needs no model part because the databases are separate. Optional desktop notification titles include the model name.
- **Done when:** two temporary models with different data and different configs ingest side by side, and tests prove that alerts, code descriptions and time zones of one do not appear in the other.

**M22 as built.**
- **Most of M22's plumbing already existed from M21** (per-model paths, `--model` on every CLI, per-model config folders, the Makefile loops), so this milestone added what was still missing and proved the isolation with a test.
- **Isolation test** (`tests/test_model_isolation.py`): two models with different VINs, platform codes in the file names, warning codes, descriptions, time zones and alert rules are ingested and evaluated side by side; the test asserts that each database holds only its own VIN, that a description in one model is not used by the other (its code stays unmapped), that each uses its own `car_timezone`, and that alerts follow each model's own `alerts.yaml` and data.
- **Ingest warnings:** a model whose folder has no export files is reported (`warning: no export files for Mazda CX60 in ...`) and, when it has no database yet, none is created (an empty file would look like a model with data); a database that holds more than one VIN is reported with the VINs masked, because a model is one car.
- **Compatibility report** (`make compat`, `mazda_dash/compat.py`): for each model, how many of the signals the views read are in its data, which are missing (with the views they feed), which are present but never valid, the two warning-flag families (signals and how many change), which export kinds were loaded, and how many signals nothing reads (`--all` lists them, `--strict` exits 1 when something is missing). On the author's CX-5 all 39 named signals are present and 33 of 200 signals are read by no view.
- **Desktop notification** titles carry the model's name ("Mazda CX-5: 2 new alerts").
- **Differences from the plan:** (1) there is no shared `config/defaults/`: a missing `alerts.yaml` or `settings.yaml` already falls back to the built-in defaults (`AlertsConfig()`, UTC and 6 h), which is the same thing without a second copy that could drift; the CLIs print a note when a file is missing. (2) The report compares signals and export kinds, not ECU and warning kinds (those are data, not something the views require). (3) `make ingest` still runs one model per call and the Makefile loops over all of them; a single `--model all` option was not needed.
- **Checked:** backend 198 tests (8 new), lint, `make demo-ingest`, and `make compat` on the real database.

## Comparing models and periods, and fuel cost (M29–M33, planned)

**Idea.** Pick two car models (say the CX-5 and the CX-60) and see the Trends metrics side by side. The numbers
already exist: `GET /api/trends/monthly?model=` answers per model since M23, so the first version needs **no new
API route** (two requests, one per model) and therefore nothing to mirror in the phone's TypeScript engine.
M28 (a real CX-60 export) is not a prerequisite: the synthetic CX-60 differs from the CX-5 on purpose, so the
feature can be built and tested now; M28 only decides later which metrics are fair to compare on real data.

### Is it useful, and what must it not claim?
Yes, for the metrics that describe **how the car is used or how it drinks fuel per distance**, and no for those that describe **how the car reports**:

| Metric | Across two models | Why |
|---|---|---|
| Distance, days driven, drives, time driving, average speed (per day) | comparable | they describe the usage; per day, so months of unequal length and different periods can be set side by side |
| Fuel consumption (l/100 km) | comparable **with a caution** | only like for like: a plug-in hybrid's l/100 km hides the electric part, and different fuels differ |
| Tire pressure (average, lowest) | caution | the recommended pressure differs per car |
| Warning events, read-outs with faults, new/distinct faults | caution | codes, how often the car logs them and what counts as a fault differ by platform |
| Different warnings (distinct codes) | not comparable | the code sets are different vocabularies |

So the page labels every metric *comparable* / *caution* / *not comparable* with the reason, never colours a difference
green or red (a different car is not an improvement or a regression), and never shows a guess as a fact (the
project's rule). Without those labels the page would invite wrong conclusions ("the CX-60 has far more warnings").

### Decisions (confirmed)
| Topic | Choice | Why |
|---|---|---|
| Where | a separate page `/compare`, not a mode of Trends | Trends is one car against its own previous month; comparing cars is another question, with its own caveats |
| Period | each car's own data, aligned by **calendar month**, by default only the months **both cars have complete** (a switch shows all data, and one for partial months) | different periods and partial months are the main way to compare unfairly |
| Basis | **per day** by default (the Trends "per day" maths, reused), and distance-weighted for l/100 km | totals depend on how long each car was observed |
| Wording | neutral and exact: "CX-60: 7.9 l/100 km, CX-5: 7.0, over 2 complete months (May–Jun)", with the difference as a plain percentage | no good/bad tones, always the number of months behind it |
| Backend | none in M29: two calls of the existing monthly route | no API change, nothing to mirror, no `make types` |
| Phone | M30, from small per-model summaries cached on the device | the phone's engine holds one pack at a time, so the other car's figures must come from somewhere else |
| Visible when | two models have data | like the model selector |

### M30 — Compare on the phone
- **Why it is not free:** the phone's engine loads one pack at a time, so `GET /api/trends/monthly?model=<other>` cannot be answered from the database that is open.
- **Mechanism:** for each stored pack the phone keeps a **summary**: the answer of `/api/trends/monthly` without a period (a few KiB of JSON), computed once by the engine when the pack is loaded and stored in IndexedDB (a new `summaries` store, keyed by model and by the pack's `savedAt`, so replacing or deleting a pack discards it). When the Compare page opens and a stored model has no fresh summary, the app loads that pack, computes the summary, stores it and goes back to the model that was on screen, with a visible "Preparing the comparison" message; the second visit is instant.
- **Engine:** `Api` answers `/api/trends/monthly?model=<other>` from the summary when no `from` / `to` is given (the Compare page never sends one); with a period it still refuses another model as today. The golden tests of each model already contain the all-time monthly answer, so a test asserts that the summary of each sample pack equals it exactly.
- **UI:** a "Compare" entry in More; offline like the rest; nothing leaves the device.
- **Done when:** the two demo packs compare on the phone in airplane mode, a replaced pack invalidates its summary, and `make mobile-test` passes.

- **Data:** `GET /api/overview?model=<id>` per model (no backend change on the Mac). On the phone the other cars' overviews come from the same cached summaries as M30 (the summary store gains the overview answer).
- **Done when:** the demo shows both cars' cards, a car with no data is not listed, and the phone page works offline from the summaries.

### M33 — Estimated fuel cost (cost per 100 km) ✅ done
**What it is, honestly:** an *estimate*, litres the car reports (the same estimate as "Fuel used (estimated)") times the fuel price **you** enter. It is not what you paid, and the dashboard says so wherever it shows the figure.
- **Configuration (per model, `config/models/<id>/settings.yaml`):** the price history, because fuel prices change and one fixed price would make old months wrong:

  ```yaml
  fuel_currency: EUR            # an ISO code; shown with Intl.NumberFormat
  fuel_prices:                  # price per litre from a date on; the last entry before a trip applies
    - {from: 2026-03-01, per_l: 1.72}
    - {from: 2026-05-15, per_l: 1.81}
  ```
  `fuel_price_per_l: 1.75` alone is accepted as one price from the start of the data. Without any price the cost metrics are empty and the cards say how to set one (never a made-up price). Validation like the existing settings: unknown keys, negative or non-numeric prices, an unknown currency, dates out of order are errors with the file name.
- **Data:** a new table `ref_fuel_prices(valid_from, per_l)` and the currency in `ref_settings` (loaded by `build_model`, like the time zone), carried by the **pack** (`TABLES` gains the table, so an older pack is refused with the existing "made by an older version" message and the phone has no copy of the values).
- **Maths (in SQL where possible, identical in Python and TypeScript):** the price of a month is the **average of the price in force on each trip, weighted by the litres of that trip** (the trip segments already carry litres); `cost_per_100km = l_per_100km × price` and `fuel_cost_est = fuel_l_est × price`, rounded like the other metrics, `None` for a month with no price or no consumption (a gap, not 0).
- **API:** two new fields on `MonthMetrics` (`cost_per_100km`, `fuel_cost_est`) and the currency (`currency` on the month rows). **Python API, TypeScript engine (`trends.ts`, `shapes.ts`), goldens and `make types` in the same change**, as the project's rule requires; the sample data of each model gets a price history (CX-5 in EUR with a mid-period price change, CX-60 with another price) so the goldens exercise it, including a month where the price changes.
- **UI:** two metrics in `trends.ts` (`cost_per_100km`: lower is better, `fuel_cost_est`: additive, per day) so they appear in Trends automatically, formatted with the currency; an Overview stat "about 7.2 EUR per 100 km" with the "estimate" note; in M29's `COMPARABILITY` table `cost_per_100km` is *comparable with a caution* (each car's own price and fuel).
- **Not in this milestone:** electricity (a plug-in hybrid's cost needs charging data no view reads yet: that is M28 material), taxes or insurance, and any price lookup over the network (the apps make no outside request).
- **Done when:** the cost figures appear on Trends and the Overview for both demo cars with the price change visible in the months, a model without a price shows the hint instead, Python and TypeScript agree on every golden, and the phone refuses an older pack with the message.

**M33 as built.**
- **Settings** (`config/models/<id>/settings.yaml`): `fuel_currency` (ISO code, required with a price) and either `fuel_prices` (a list of `{from, per_l}`, dates strictly increasing) or `fuel_price_per_l`; every mistake (no currency, a currency without a price, both forms, a zero or negative or non-numeric price, a bad date, dates out of order, an unknown key) is a `ValueError` that names the file (`tests/test_fuel_cost.py`, 15 cases). Without a price nothing is stored and nothing is shown. The real `cx5` and `cx60` settings files set no price.
- **Data:** table `ref_fuel_prices`, the currency in `ref_settings`, a view `v_fuel_prices` (each price's span; **the earliest price also applies before its own date**, so every trip has a price once any price is set, a decision the plan left open). The pack carries the table (`TABLES`, and the phone refuses a pack without it with the existing "older version" message, so existing phone packs must be made again).
- **Maths:** each trip is priced with the price in force on its day (`LEFT JOIN v_fuel_prices`, the same `PRICED` fragment in Python and TypeScript); `cost_per_100km` = 100 × Σ(litres × price) / Σ km and `fuel_cost_est` = odometer distance × that cost per km, rounded to 2 decimals; both `None` for a month with no price (a gap). New fields: `cost_per_100km`, `fuel_cost_est`, `currency` on `MonthMetrics`, and `cost_per_100km_in_range`, `currency` on the Overview. **Python, the TypeScript engine, the goldens and `make types` changed together**; the goldens of both sample cars contain the cost figures and the 802 phone tests (Python against TypeScript) agree on every one, including the CX-5's month with a price change.
- **Demo data:** the sample generator now also writes `settings.yaml` next to each car's exports (time zone and price from its profile: the CX-5 in EUR with 1.72 changing to 1.81 on 15 May, the CX-60 in EUR with the single-price form 1.79); `make demo`, the goldens and the sample tests ingest with it (`ingest --settings`), so the demo never reads or changes your real settings. The CX-5 and CX-60 data files are byte for byte unchanged.
- **UI:** two metrics in `trends.ts` (`money: true`, `¤` in the unit replaced by the currency: "EUR/100 km", "EUR/day"), so Trends shows them; the Overview says "about 12.29 EUR per 100 km (estimate)"; every help text says estimate and "not what you paid"; without a price the Trends page leaves the cards out and says which settings to add. On the compare page the two metrics are *compare with care*, and **amounts in two currencies, or a price set for only one car, are shown but not compared**, with the reason (tests).
- **Not in this milestone, as planned:** electricity (M28 material), taxes and insurance, any price lookup over the network.
- **After pulling:** run `make model` once so an existing database gets the new table and view (the README's usual step), and `make mobile-pack` for the phone.
- **Checked:** backend 267 tests (25 new), frontend 103 (9 new), `make mobile-test` 802, lint, `TZ=UTC make types sample-data` (only the new `settings.yaml` files and the regenerated types differ), and in the browser: the cost cards on Trends and Compare and the Overview line with the demo cars, and the "no fuel price" hint with a copy of your real CX-5 database (rebuilt in the copy only; your own database was not touched).

## Open questions

- **Meaning of the `$xxx` warning codes, the DTC status flags, the alarm codes, the non-zero values of the car's own warning flags and the 128 warning-lamp flags.** Still open: Mazda does not publish them. `$210` appears in ~98% of events and is probably informational, but that is a guess. Descriptions are meant to be filled in by the owner in `config/codes/`; the dashboard offers hints (what appears around a flag) as a starting point.
- **Time zone of `COPIED_DT_TM` / `fileid_datetime`.** Assumed UTC (the diagnostic tool dump states its own offset, which is applied). The tire measurement clock is the car's *local* time and has its own setting (`car_timezone`, M19).
- **Several vehicles.** Different models are supported (one database, folder and configuration each); two cars of the *same* model are not separated (one car per model folder, `make ingest` warns about a second VIN).
- **Other models, markets and firmware.** Only one real export (a CX-5, Europe, 2026) was available; others may differ. Multi-model support is built (M21–M27); what a real CX-60 export needs is M28, not started.
- **What is fair to compare across models?** Proposed in "Comparing models and periods" (usage per day, fuel per distance with a caution); the real answer needs a real CX-60 export (M28), in particular for a plug-in hybrid's consumption.
- Resolved: the warnings table is mostly repeats of the same few codes, so alerts are based on new codes and unusual days, not on every row.
