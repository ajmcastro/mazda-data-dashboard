# Mazda CX-5 Data Dashboard — Implementation Plan

Personal dashboard to analyse the data Mazda exported for my CX-5 (see `CLAUDE.md` for a description of the files in `data/`), with alerts for relevant events. The repo may be open-sourced later, so privacy and reproducibility are designed in from the start.

## Decisions

| Topic | Choice | Why |
|---|---|---|
| Python tooling | `uv` + `Makefile` | Preference; reproducible with `uv.lock` |
| Storage | **DuckDB** (single file) | Columnar and analytical; reads the wide `dtc-ssr` CSV and mixed timestamps well; `read_csv` makes re-ingestion trivial. SQLite would work but is clumsier for this kind of analytics |
| API | **FastAPI** | Thin read-only layer over DuckDB; typed responses |
| Frontend | **React + Vite + TypeScript** | Flexible for alerts, drill-downs and a polished UI; Streamlit is faster to start but limiting for a long-lived, shareable project |
| Charts / tables | Recharts (or ECharts) / TanStack Table | Decide in milestone 4 |
| Tests | pytest (backend), Vitest (frontend) | |

## Privacy / open-source rules

- `data/`, `*.duckdb` and `.env` are gitignored. The VIN and personal data never get committed.
- Provide `sample_data/` with **synthetic** data in the same format (generated by a script), so others can run the app.
- Mazda-specific code descriptions live in an editable mapping file (`config/codes/*.yaml`); only publish codes whose meaning is public or user-supplied.
- Add a licence (MIT suggested) and a README before publishing (milestone 7).

## Makefile targets (target set)

`setup` (uv sync + npm install), `ingest`, `api`, `web`, `dev` (api + web), `test`, `lint`, `format`, `sample-data`, `clean`.

## Milestones

Each milestone is implemented only when requested ("start implementing milestone N") and ends with a short summary and a check that it works.

### M1 — Data exploration & data dictionary
- Scaffold `backend/` with `uv`, the root `Makefile`, `.gitignore` (data, db, node_modules).
- Notebook/script profiling every file: row counts, date ranges, null rates, distinct values, duplicates.
- Produce `docs/data-dictionary.md`: columns, units, join keys, timestamp formats, quirks.
- Output: findings that may adjust milestones below.

### M2 — Ingestion into DuckDB
- Parsers for each CSV (typed columns, UTC-normalised timestamps, empty → NULL, `_value`/`_validstatus` handling).
- Parser for the diagnostic `.txt` (sections → key/value/unit rows).
- Split `WARNING_LIST` into one row per warning code; normalise DTC code and status.
- Idempotent `make ingest` (re-running with newer exports doesn't duplicate rows; dedupe on `X_TRANSACTION_ID` or timestamp keys).
- Tests with small fixtures.

### M3 — Domain model & code lookups
- Views/tables for: warning events, DTC events (+ header + snapshot), vehicle status timeline, diag-tool counters.
- Editable code-description mappings (warnings, DTCs, ECUs) with "unknown" fallback.
- Derived metrics: odometer over time, fuel consumption per trip, warning/DTC frequency.

### M4 — API + dashboard skeleton
- FastAPI endpoints for the views above; OpenAPI types shared with the frontend.
- Vite/React app: overview page (key stats, odometer/fuel charts), warnings page, DTC explorer, status/doors page.
- `make dev` runs both.

### M5 — Alerts engine
- Rule definitions in YAML: new DTC never seen before, recurring DTC/warning above a threshold, burglar alarm triggered, abnormal fuel consumption, invalid signals, long gaps in data.
- Alerts persisted in DuckDB with severity and status (new / acknowledged); notifications panel in the UI.
- Optional later: desktop/email notifications after each ingest.

### M6 — Diagnostic report & deep dives
- Diag-tool report view (Mode 9, VOD counters, OCC sections).
- DTC freeze-frame viewer (snapshot data around each fault); compare reports over time if more tool dumps are added.

### M7 — Polish & open-source readiness
- Synthetic sample data generator, README with screenshots, licence, CI (lint + tests) on GitHub Actions.
- Audit git history and files for VIN or personal data before the first push.

## Open questions (to resolve during M1)

- What are the real meanings of the `$xxx` warning codes and DTC status flags? Are any publicly documented?
- Do multiple VINs / future exports need support? (Design assumes yes; costs little.)
- Is the 7k-row warnings table mostly repeats of the same events? Affects de-duplication and alert thresholds.
