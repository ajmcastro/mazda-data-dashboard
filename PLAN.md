# Mazda Data Dashboard — Plan and status

Personal dashboard to analyse the data Mazda exported for my cars (a CX-5, and a CX-60 set up the same way), with alerts for relevant events. The files in `data/` are described in [docs/data-dictionary.md](docs/data-dictionary.md); how to use the app is in [README.md](README.md); [CLAUDE.md](CLAUDE.md) is the tour of the code. The repo is meant to be open-sourced, so privacy and reproducibility were designed in from the start.

**Status: M1–M68 are done except M28** (adapting to a real CX-60 export: on hold until there is one): the Mac dashboard (M1–M11), the offline iPhone app (M12–M16, live on GitHub Pages and tested on a real iPhone), four features built from the car's own signals (M17 next oil change, M18 the car's own warnings, M19 tire reading time, M20 warning-lamp flags), several car models (M21–M27), comparing cars and periods and the estimated fuel cost (M29–M34), more from the data already loaded (M35 when the car is used, M36 fault context, M37 who rides), the car in 3D (M38–M41 the status view on the Mac and the phone, M42–M44 each car's own shape traced from the owner's photos), and eighteen milestones of "more value from the same data" (M45–M62: units, data health, fill-ups, the driving pattern, the day page, a service log, the tire leak and maintenance forecasts, import from the dashboard, a report for the workshop, six follow-ups of the 3D car, code description packs, and Portuguese as a second language). Learning from the data has begun: **M63 warning episodes, M64 unusual status reports, M65 consumption change points, M66 driving routines, M67 fault comeback and M68 battery voltage are done; M69–M71 are planned, not started** ("Learning from the data"). Other ideas are under "Ideas not built". This file keeps the design decisions and the plan each milestone was built from, with an "as built" note where the result differs; it is a design log, so some sections describe the plan in the future tense before the "as built" note that follows them.

## Decisions

| Topic | Choice | Why |
|---|---|---|
| Python tooling | `uv` + `Makefile` | Preference; reproducible with `uv.lock` |
| Storage | **DuckDB** (single file) | Columnar and analytical; reads the wide `dtc-ssr` CSV and mixed timestamps well; `read_csv` makes re-ingestion trivial. SQLite would work but is clumsier for this kind of analytics |
| API | **FastAPI** | Thin read-only layer over DuckDB (plus acknowledging alerts); typed responses; OpenAPI schema generates the frontend types |
| Frontend | **React + Vite + TypeScript** | Flexible for alerts, drill-downs and a polished UI; Streamlit is faster to start but limiting for a long-lived, shareable project |
| Charts / tables | Recharts / a small sortable `DataTable` component | Chosen in M4; TanStack Table v9 was skipped (new API, not needed) |
| Tests | pytest (backend), Vitest (frontend) | |
| Time | All timestamps stored as naive UTC; periods are inclusive UTC days | One convention end to end; the browser shows local time |
| Alerts | Rules in YAML, each alert raised once per `dedup_key` | Acknowledging is a workflow; rules are tunable without code |
| Period filter | `from` / `to` in the URL and the API | Bookmarkable; state (active faults, alerts, diagnostic report) is deliberately not filtered |

## Privacy / open-source rules

- `data/` (every model's folder), `db/`, `*.duckdb`, `*.cx5pack` (phone data packs: they hold the VIN) and `.env` are gitignored. The VIN and personal data never get committed.
- `sample_data/<model>/` holds **synthetic** data in the same format (generated by `make sample-data`), so others can run the app; `make audit` fails if it ever holds a VIN other than the synthetic ones.
- Mazda-specific code descriptions live in editable files (`config/models/<id>/codes/*.yaml`, per model, never shared); only publish codes whose meaning is public or user-supplied.
- MIT licence and README are in place (M7). Before publishing, run `make audit`: it looks for the VINs and positions found in `data/` in every publishable file and in the whole git history, and lists commit author emails.

### M8 — Date-range filter (from / to) ✅ done
- **Backend:** one shared `date_range` dependency (`from`, `to`; inclusive days, UTC; `from <= to` else 422) applied in SQL to the time-based endpoints: odometer, fuel, trips, status timeline, doors, warnings (frequency, daily, events), fault events and read-outs, overview figures. Without parameters nothing changes (all time).
- **Not filtered (state, not events):** faults active in the latest read-out, the alerts list, and the diagnostic-tool report (it has its own picker, M10).
- **Frontend:** a date-range bar with two date inputs; the range lives in the URL (`?from=2026-06-12&to=2026-07-12`) and every query key includes it. Overview tiles describe the chosen range.
- **Edge cases:** an empty range shows a clear message; the range survives navigation between pages.
- *As built:* `GET /api/span` bounds the date pickers; `fuel/monthly`, `warnings/frequency` and `dtcs/frequency` re-aggregate inside the endpoint to honour the range (they mirror the corresponding views).

### M9 — Quick ranges (presets) ✅ done
- Presets: **Last week**, **Last 2 weeks**, **Last 30 days**, **Last 60 days**, **Last 90 days**, **All time**. The active preset is highlighted; editing a date manually clears the highlight (custom range).
- **Decision (confirmed):** presets count back from the **most recent data point**, not from today. Exports are snapshots, so "last 30 days" relative to today would be empty after a few weeks without a new export. The bar shows the resolved dates.
- The last preset is remembered in the browser (default for new visitors is All time; a link with dates wins). Keyboard accessible (a native radio group), works on phone width.
- Pure date logic (`resolvePreset`, `matchPreset`, `restoreRange`) lives in `lib.ts` with unit tests, including month ends and datasets shorter than the preset.

### M10 — Choose any diagnostic-tool report ✅ done
- The report selector is **always visible** and lists each report as "date · odometer · file", newest first, with the selection in the URL (`?report=`; `?compare=` for the comparison).
- A **report history** panel: lifetime km, lifetime l/100 km, ignition cycles, engine hours, monitors passed and faults listed per report, with small charts when there are 2+ reports. The "compare with" table stays and always reads from the earlier report to the later one.
- Ingest: several `*diag-tool*.txt` files (even with the same date or VIN) load as separate reports; an identical copy under another name is skipped; re-running adds nothing.
- `sample.py` writes **three** diagnostic reports (as if downloaded at three different dates); tests cover the report list, history, switching and comparison across dates.
- *As built:* `GET /api/diag/history`. With real data there is one dump today; further dumps appear once their `.txt` files are in `data/` and `make ingest` is run.

### M11 — Monthly comparison page ("Trends") ✅ done
A page showing how each metric evolved month by month, with the change against the previous month.
- **Presentation:** a card per metric with a bar chart across all months (latest highlighted), the current value, and "x % more / less than May" with an arrow. Colour reflects whether the change is good or bad for that metric (less fuel use is green; more warnings is red; distance driven is neutral). A table view (months as columns, change underneath) for exact numbers.
- **Incomplete months:** the first and last month are usually partial, so they are marked "partial" and totals can be shown **per day covered** via a toggle. Months without data show a gap, not zero; a missing previous month shows "no previous month".
- **Backend:** `GET /api/trends/monthly` returns one row per calendar month in the selected period (including days covered); the change and its good/bad direction are computed in the frontend (unit-tested).
- *As built, and where it differs from the plan:*
  - Monthly figures are computed in `api/trends.py` instead of a `v_monthly_metrics` view, so the date range applies *before* aggregation (a month cut by the period only counts its days inside it and is reported as partial).
  - *Alerts raised* is not a metric: alerts are only evaluated for the last `lookback_days` each time you run `make ingest`, so older months would always show 0.
  - *Trips* became two metrics, **Drives recorded** (stretches between status snapshots) and **Days driven**, because the car's snapshots are not true trips. *Distance* comes from the odometer, not from summed stretches (which cover only part of it); *fuel used* is estimated as distance × consumption.
  - *New faults* excludes faults first reported on the first day of diagnostic data, which may have existed long before the data begins.

## Standalone offline app for iPhone (M12–M16, built)

**Goal.** Use the dashboard on an iPhone (iOS 27 is the target), with the data on the phone, **without the Mac being on or reachable**. **Hard constraint:** the current app must keep working exactly as today (`make dev` → `http://localhost:5173`, `make demo`, all tests). The new app therefore lives in its own folder, **`mobile/`**, with its own `package.json`, build and tests. The existing `backend/` and `frontend/` get only the small, tested changes listed under "What changes in existing code".

### How it works

```
 on the Mac (unchanged)                      on the iPhone (new, offline)
 data/ ─ make ingest ─▶ db/mazda.duckdb      ┌──────────────────────────────────────────────┐
                           │                 │ installed web app (static files, cached)     │
              make mobile-pack (new)         │   same screens as today (reused from         │
                           ▼                 │   frontend/src)                              │
                 db/mazda.cx5pack ──AirDrop / Files / iCloud Drive──▶ "Import data"        │
                 (zip of Parquet + manifest) │   DuckDB-WASM + TypeScript "API" ◀── IndexedDB│
                                             └──────────────────────────────────────────────┘
```

- **A data pack.** `make mobile-pack` (new, in `backend/`) exports the database tables to **Parquet** files plus a `manifest.json` (pack format version, creation time, row counts, newest data day) in one zip, `db/mazda.cx5pack` (gitignored). Parquet, not the `.duckdb` file, because the browser's DuckDB is a different, independently versioned build than this project's (backend: DuckDB 2.0.0; `@duckdb/duckdb-wasm` is numbered 1.33.x), and the `.duckdb` storage format is not guaranteed to open across versions, while Parquet is.
- **The same SQL.** The app loads the Parquet tables into DuckDB-WASM and runs the existing `backend/src/mazda_dash/model/views.sql` unchanged (imported from the backend folder at build time, so there is one source of truth). Code descriptions need no YAML parsing: the `ref_*` tables travel inside the pack.
- **The same screens.** The standalone app reuses the existing React pages and components from `frontend/src` through a Vite alias. Only the data layer is swapped: the pages talk to `/api/...` through one `openapi-fetch` client, and in the standalone app that client's `fetch` is replaced by an in-browser implementation of the same routes (28 when this was planned, 33 by M20). So the screens, types and URL parameters (`?from=`, `?report=`) are identical.
- **Alerts.** Alert rules run on the Mac during `make ingest`; the pack carries the resulting `alerts` table. Acknowledging an alert on the phone is stored on the phone (IndexedDB) and layered over the pack's alerts. The phone does not evaluate rules (that would mean porting the alert engine; not in scope).
- **Installing without a Mac.** An iPhone can only install an offline web app (service worker) from an **HTTPS** address, not from a Mac on the local network. The plan is to host the **static build, code only**, on GitHub Pages (or any static host). The site never receives any data: the pack is imported from the phone's own storage and never leaves it. The site also offers "Load demo data" so anyone can try it.
- **Updating the data.** On the Mac: ingest a new Mazda export as today, run `make mobile-pack`, send the pack to the phone, tap **Import data**. Importing replaces the previous pack on the phone (acknowledgements are kept).

### What changes in existing code (the only seams)

1. `frontend/src/api/hooks.ts`: the `createClient(...)` call moves into `frontend/src/api/client.ts` so the standalone build can substitute its own client. No behaviour change; covered by the existing typecheck, lint, tests and build.
2. `backend/`: **new** files only (`pack.py`, tests, a `make mobile-pack` target). Nothing existing is modified except the Makefile gaining targets.
3. CI: new jobs for `mobile/`; the existing jobs stay as they are.
4. Responsive fixes in `frontend/src` (see "Phone layout audit" below): CSS under narrow-width media queries plus a few layout tweaks, so the Mac app also behaves on a narrow window. Desktop widths must look unchanged (checked with before/after screenshots).

#### M12 — Feasibility spike and decision gate ✅ done (final GO, confirmed on a real iPhone)
Prove the risky parts before building the rest.

**Finding after the real iPhone, rounds 1 and 2: even on a phone that runs code 60–70× slower than the Mac (see the processor row; probably JIT off), the trimmed pack gives a working database in roughly 1.5–2.5 s once the engine is cached, and each query takes tens of milliseconds, so a screen shows in well under a second.** Cheapest fix already made: `signal_readings` held 200 signals of which the views read 24 (4,546 of 41,680 rows), so packs are now trimmed to those by default (`--all-signals` restores everything). On the Mac this makes table loading about 7× faster (128 ms to 18 ms), views 3× and the typical page's queries 3.5×, with identical view results (tested); compression (zstd, snappy, none) makes no measurable difference, so zstd stays. DuckDB's browser OPFS persistence was tried (so the tables would not be rebuilt at each launch) and **did not persist** in this version (the file stayed empty, DuckDB logged "buffering"), so it is dropped; an alternative is saving the database file's bytes in IndexedDB if loading is still too slow after trimming.

**Decision gate: GO.** The risks that could have stopped the plan did not materialise: the SQL needs no changes, results are identical in Chrome, desktop Safari, **iOS Safari 27** and on a **real iPhone**. Speed, the only open question, is answered: round 1 (full pack, first download of the engine) took 9.3 s; round 2 (trimmed pack, engine cached) is about 1.5–2.5 s even on this slow phone. The first install still downloads the engine once (7.7 MB gzip, 5.2 MB brotli on a host that compresses; the Mac's test server did not compress, which is why round 1 looked so bad). M12 is **closed with a final GO**. The fallbacks in the milestone text are not needed.

- Ship the **trimmed** pack by default (done in M12); keep the app shell responsive while the engine starts (show the screen skeleton and a progress line at once; start the engine and load the data in the background).

### Limits (by design)
- **Read-only viewer.** New Mazda exports still go through `make ingest` on the Mac, then a new pack to the phone. Parsing Mazda's zip/CSV files on the phone would mean porting the ingestion code; not planned.
- Alerts are not re-evaluated on the phone.
- Two implementations of the API must be kept equal; the golden tests make drift visible but cost maintenance.
- iOS decides how long web-app storage survives; keep the pack file (iCloud Drive or Files) as the source of truth.

### Risks and how the plan handles them

| Risk | Handling |
|---|---|
| DuckDB-WASM too slow or too big on an iPhone | measured first, in M12, with a written go/no-go and fallbacks |
| SQL differences between DuckDB 2.0.0 and the WASM engine | run all of `views.sql` in M12; adapt the SQL only if needed, keeping Python and WASM results identical |
| The TypeScript API drifting from the Python one | golden contract tests (M13), regenerated and diffed in CI |
| iOS evicting stored data | persistence request, detection and one-tap re-import (M15); the pack file is the backup |
| Phone with the JIT compiler off (Lockdown Mode or similar): code runs 10–70× slower | measured: still ready in about 2 s and queries in tens of ms; the app shows its screen skeleton immediately, and the README explains how to exclude the site from Lockdown Mode for full speed |
| Stale cached app after an update | versioned precache and an update prompt (M15) |
| Privacy of hosting | the host only ever serves static code; CSP `connect-src 'self'`; verified by blocking the network (M15, M16) |
| Breaking the Mac app | separate folder; only the one-line client seam in `frontend/`; both apps run in CI |

### Decisions

1. **Folder name: `mobile/`.** Confirmed.
2. **Host the app's code on GitHub Pages** (public, code only; no data ever in the repo or the site). Confirmed.
3. **Move the data pack by AirDrop / Files / iCloud Drive.** Confirmed.

### M18 — Alerts from the car's own warnings

- **UI:** a "Car warnings" panel on Status (all clear, or which flag is on since when) and a row in the Overview alert strip.
- **Alert rule** `car_warning_flag` (default severity warning; `critical` can be set per flag in the file): plain-language titles ("The car reports a tire pressure warning: rear left"), raised once per episode, event-based so the 30-day lookback applies. It complements the user-set low-pressure rule (`low_tire_pressure`), which stays.
- **Sample data** gets a rear-left tire warning flag that comes on shortly after the existing slow leak, so the demo shows both.
- **Open point:** the meaning of non-zero values (1 vs 2 …) is unknown; the plan treats any non-zero as "warning" and shows the raw value in the detail text. If a real value ever appears, `config/codes/` gets an optional label file for it.

**M18 as built.**
- `v_car_warning_readings` (every valid reading of the nine flags, with a label, display order, raw value and `is_on`) and `v_car_warning_episodes` (runs of consecutive readings with a flag on; `ongoing` = the run includes the flag's latest reading), both in `views.sql`. The plan's single `v_car_warnings` became these two, so the API and the alert share the run logic. The flag list is one `CASE` using the `signal = '...'` form, so the phone pack includes the signals by itself (a test keeps the view, the alert config's `CAR_WARNING_FLAGS` and the pack signals in step). ### M19 — Tire reading time
- **Time zone first:** the measurement time is in the car's local time. Add `car_timezone` to a small settings file (e.g. `Europe/Lisbon`, with a one-line check that suggests the zone from the data: compare the measurement clock with the snapshot's UTC time) and convert to UTC. Must handle the clock change in late October and invalid parts (`255`, `0` year).
- **View and API:** `v_tire_readings` with `measured_at` (UTC), the snapshot time, and the age of the measurement at snapshot time; consecutive snapshots that repeat the same measurement are one reading.
- **UI:** the tire panels say "measured 18:02, 41 min before this snapshot"; the Status tire chart uses the measurement time on its axis (fewer duplicate points); stale readings (older than a configurable number of hours) are marked.
- **Alerts:** `low_tire_pressure` keys on the measurement time instead of the snapshot time, so one low reading counted in several snapshots raises one alert.
- **Done when:** both implementations convert times identically (DST edge cases in the goldens) and the demo data has readings whose measurement is older than the snapshot.

**M19 as built.**
- **Settings file** `config/settings.yaml` (`car_timezone`, `tire_stale_hours`), loaded into a `ref_settings` table by `build_model` (unknown settings, an invalid time zone name or a stale limit of 0 are errors; defaults UTC and 6 h when the file is missing). The table is in the data pack (`TABLES`), so the phone reads the same values; the phone app refuses an older pack without it with a clear message. `make timezone` (`timezone_check.py`) tells whether the configured zone fits the data and groups the zones that do by the clock offset they imply (it cannot tell apart zones that behaved alike during your data, so it says to choose the one where you live).
- **Views** (`views.sql`): `v_tire_snapshots` (per status snapshot: `measured_at` in UTC, `age_minutes`, `stale`) and `v_tire_readings` (one row per distinct measurement; repeats are folded, with first and last age and the number of snapshots; a snapshot with no valid time is its own reading with `time_known = false`). **The conversion is a single `make_timestamp(epoch_us(timezone(zone, local_time)))`** because the in-browser DuckDB crashes or cannot bind `timezone()` calls nested in each other; Python and the browser agree on every case tested.
- **API:** `GET /api/status/tires` (period-aware, by measurement time) and three new fields on the Overview `status` (`tire_measured_at`, `tire_age_minutes`, `tire_stale`).
- **Alert:** `low_tire_pressure` now keys on the measurement time (`v_tire_readings`), so a low reading repeated in several snapshots is one alert dated when it was measured. Snapshots without a time behave as before.
- **UI:** the Overview tire panel says "measured 30 Jun, 18:56, 5 min before this snapshot" (amber "old" when stale); the Status tire chart plots one point per measurement at the time it was taken with a note counting stale and unknown-time readings. Wording is in `fmtAge` / `tireMeasuredNote` / `tireReadingsNote` (tested).
- **Phone:** `tireReadings` in the TypeScript engine, the extended status, and goldens. **DST edge cases are in the goldens**: `contract.py` adds 17 clock readings to the temporary database it records from (the forward and back clock changes of Lisbon on 2026-03-29 and 2026-10-25, a leap day, impossible dates, 255 and year 0), never to the sample files, and the browser engine reproduces every one (also on the author's real data).
- **Sample data:** the demo car measures 2–41 minutes before each drive ends, so its clock runs through the March clock change; snapshots taken after the car stood still for hours show old measurements (9 stale, one of 62 hours), nine repeats are folded, and one snapshot has no valid time. Added without changing the random stream (only the status CSV differs); `tzdata` was added as a backend dependency so the zone database is the same everywhere.
- **Real data (author's export):** with `Europe/Lisbon` the measurement times fit perfectly (196 snapshots, none in the future, median 12 minutes old, oldest 26 hours, 6 snapshots stale, 185 distinct measurements). Run `make model` once to get the settings table and the views.
- Pitfall found on the way: `at` is a reserved word in DuckDB (the column is `reading_at`).

### M20 — Warning-lamp flags (the 128 bit flags)
- **View and API:** `v_warning_flags`: per flag, readings set, share of readings, first and last seen, and the timeline of when it was on; only flags that ever change are listed by default. `GET /api/status/warning-flags`.
- **Labels:** user-supplied meanings in `config/codes/warning_flags.yaml` (like `warnings.yaml`: title, severity, notes); unmapped flags appear in `make unmapped` and the dashboard's unmapped list.
- **Decoding aid:** for each flag that changes, show which `$` warning codes and which diagnostic faults appear around the times it is on (for example "set in 94 snapshots; `$…` codes co-occur in N of them"), clearly marked as a *hint*, not a fact. This is research support for filling in `warnings.yaml` and the flag labels.
- **UI:** a "Warning lamps" panel on Status with the timeline; flags set on the day of a diagnostic report are called out.
- **Alert rule** `new_warning_flag`: a flag that has never been set before is set for the first time (like `new_warning_code`).
- **Done when:** the panel, hints, labels and alert work on sample and real data, with identical results in both implementations.

**M20 as built.**
- **Views** (`views.sql`): `v_warning_flag_readings` (every valid reading of the 128 flags, **only for flags that take more than one value**), `v_warning_flag_episodes` (runs of consecutive readings with a flag on; `ongoing`) and `v_warning_flags` (per flag: readings, readings on, share, first/last on, on now, your title/severity/notes, whether it was first set on a diagnostic-report day, number of runs). `v_unmapped_codes` gained kind `warning flag`, so `make unmapped` and the Overview's "N codes have no description yet" include flags without a meaning.
- **Labels:** `config/codes/warning_flags.yaml` (title, severity, category, notes, like `warnings.yaml`; ships empty with a clearly marked made-up example, never guesses) loaded into `ref_warning_flags` by `lookups.py`.
- **API:** `GET /api/status/warning-flags` (flags in power-train-then-body order, every run, the time span of the readings; a state endpoint) and `GET /api/status/warning-flags/hints?flag=&window_hours=` (404 for a flag that does not change). **Hints:** for each warning code and each fault, in how many readings with the flag on / off it appears within the window (default 2 h, up to 48), as a share of the readings with it on / off; only things more common when the flag is on are listed, ranked by that difference (at most 8 each). One request takes about 30 ms on the real data. Presented as "a hint, not a meaning". On the author's data one flag (`vdt_7_warningbody_2_44`, set 3 times) is on exactly when warning `$1B4` is near (100% of its readings against under 1% otherwise): the kind of lead this is for.
- **Alert `new_warning_flag`** (default info; severity comes from your yaml once you describe the flag; `ignore_flags` with names checked against the `vdt_2_warningpt_N_N` / `vdt_7_warningbody_N_N` pattern): a flag first set inside the lookback window, one alert per flag, mentioning when it is a diagnostic-report day and, without a meaning yet, where to look and where to describe it. On the author's data the two power-train flags first set on 15 Oct will raise one alert each on the first run.
- **UI:** a "Warning lamps" panel on Status: one row per changing flag (your title or "Power train flag 23", the car's name, badges *on now* / *first set on a report day* / *no meaning yet*, a timeline bar across the data, "on in 94 of 214 readings"), opening a row shows its details and the hints with a 0.5 / 2 / 6 / 24 h window selector. Wording and timeline maths are `lampLabel` / `lampBars` / `fmtShares` (tested).
- **Phone pack:** the pack scans `views.sql` for signal *families* written `starts_with(signal, '<prefix>')` (`signal_prefixes` in the manifest) and exports only the family members that vary, so 128 flags cost 4 flags' rows (27,392 → about 800 rows on the real data; the real pack is 468 KiB, smaller than before). `ref_warning_flags` joined `TABLES`; the phone app refuses an older pack that lacks the table or the families. The browser engine reproduces Python on every golden, including hints for each flag at several windows and the 404 / 422 cases, and on the real data.
- **Sample data:** six flags as plain columns like the real file: two that never change (and so never appear), one on in the mornings, two set only on diagnostic-report days, one that first appears in the last days (raising the new-flag alert). Derived from the clock only, no random numbers.
- **Real data (author's export):** 4 flags change (`vdt_7_warningbody_1_30` on in 94 of 214 readings and 52 runs, `vdt_7_warningbody_2_44` 3, `vdt_2_warningpt_1_23` and `vdt_2_warningpt_2_46` 4 each, the last two first set on the day of the diagnostic report); none has a meaning yet. Run `make model` once.
- Pitfall found on the way: a view that lists constant flags makes the pack's copy (without them) differ in the view fingerprints; the readings view itself is therefore limited to changing flags, which makes the Mac database and the pack agree by construction.

### Decisions (all confirmed)
1. **Order:** M17 oil, M18 car warnings, M19 tire time, M20 lamp flags (easiest and most useful first). Confirmed.
2. **Time zone (M19):** a setting in a small config file, with a suggestion from the data (not the browser's time zone, which would be wrong when travelling). Confirmed.
3. **Default thresholds:** oil change due below 1,000 km; tire data "stale" after 6 hours; car warning flags severity `warning`. Confirmed.
4. **Phone app:** all four ship to it in the same milestone (the engine and golden tests are extended each time), not as a separate catch-up. Confirmed.

## Several car models (M21–M27, built; M28 conditional)

**Goal.** Support more than the CX-5 (first target: the CX-60) in the whole app, not only in ingestion: each model has its own raw exports in its own folder, its own database and configuration, and the dashboard (Mac and phone) lets the user choose which model to look at. **Hard constraints:** a CX-5-only install keeps working, with no visible model chrome beyond a label; nothing from one model leaks into another (data, alerts, code descriptions); the privacy rules (no VIN committed, no real pack deployed) apply to every model.

### What the code looks like today (why this is mostly plumbing)
- Ingestion is already model-agnostic: files are found by the `_<kind>-` part of the name (`*_war-*.csv`, …), so the platform code in the name (`24pf`) is not used. The `rts`/`vis`/`alt` signals are stored in long form and views read them by `signal = '<name>'`, so a signal that a model lacks is simply an empty reading, not an error.
- What is single-car by construction: one `data/` folder, one `db/mazda.duckdb`, one `config/` (code descriptions, alert rules and `car_timezone` all describe *the* car), `MAZDA_DB` read by `api/db.py`, no model in the frontend's query keys or URLs, and one pack in the phone app's storage.

### Decisions (confirmed)
| Topic | Choice | Why |
|---|---|---|
| Storage | **One DuckDB file per model** (`db/<model>.duckdb`), not one shared database with a `model` column | `views.sql`, the alerts engine, the pack, the TypeScript engine and every golden test stay as they are; a model cannot leak into another; deleting or resetting one model is one file. A shared database would mean a model column in every table, view, key and `dedup_key` |
| Model id | A short slug: `cx5`, `cx60` (lower case, `[a-z0-9]+`); the display name and platform code live in `model.yaml` | Used in folder names, URLs, file names and the API |
| Raw data | `data/<model>/` (e.g. `data/cx5/`, `data/cx60/`), same file kinds as today | What was asked for. Existing flat `data/` keeps working as the `cx5` folder during migration (see M21) |
| Configuration | `config/models/<model>/` with `model.yaml`, `settings.yaml`, `alerts.yaml`, `codes/*.yaml`; a missing `alerts.yaml` or `settings.yaml` falls back to a shared `config/defaults/` (never the code descriptions) | Warning codes (`$182`), DTC meanings and flag labels can differ per platform, so descriptions must not be shared; alert thresholds and time zone usually differ per car |
| API | Every route takes `model` (query parameter, default = the only model, or the first in `models.yaml` order); `GET /api/models` lists them | Same pattern as `date_range`; one FastAPI app serves all models, one short-lived read-only connection per request on the chosen file |
| Frontend | The model is part of the URL (`?model=cx60`) and of every query key, carried by the same link helpers as the date range; the last choice is remembered in `localStorage` (`cx5.model`) | Bookmarkable; no stale data from another model; same mechanism as the range, so it is already proven |
| Phone | One pack per model, several packs stored on the device, a model switcher in the app | A pack is already one database; the engine is untouched |
| Model-specific features | Out of scope at first: pages show whatever the model's data has; a model can hide a page with `pages:` in `model.yaml` | A plug-in hybrid (CX-60 PHEV battery and charging signals) needs a real export to design; see M28 |

- **Registry:** `config/models.yaml` lists the models in display order; each has `config/models/<id>/model.yaml` (`id`, `name` such as "Mazda CX-60", optional `platform` such as `24PF`, optional `pages` to hide pages, optional `default: true`). A new `mazda_dash/models.py` loads and validates it (slug rules, unknown keys are errors, duplicate ids, missing folder) and gives the rest of the code one `Model` object (`data_dir`, `db_path`, `config_dir`). With a single model the app behaves as today.
- **Folders:** raw files for a model go in `data/<id>/`, the database is `db/<id>.duckdb`, the sample data in `sample_data/<id>/`. `.gitignore` already covers `data/` and `db/`; add nothing that could commit a model's real files.
- **Migration of the existing CX-5 install (no data lost):** `make migrate-models` moves `data/*.csv|txt` to `data/cx5/`, `db/mazda.duckdb` to `db/cx5.duckdb` and `config/{settings,alerts}.yaml`, `config/codes/` to `config/models/cx5/`, after printing what it will do and asking; it refuses to overwrite. Until it is run, a flat `data/` and `db/mazda.duckdb` are still read as `cx5` with a one-line notice, so nobody's install breaks on `git pull`. `MAZDA_DB` keeps working as an override for one model (tests, demo).

### M22 — Per-model ingest, configuration and alerts ✅ done
- **Ingest:** `ingest(model)` reads `data/<id>/` into `db/<id>.duckdb` and builds the model with that model's config; the CLI takes `--model` (default: all). A model folder with no recognisable files is reported, not silently skipped. The VIN-per-file check warns when one model's folder contains two different VINs (the plan assumes one car per model; see "Open questions").
- **Config per model:** `build_model` takes the model's `config/models/<id>/` (codes, `settings.yaml` with its own `car_timezone` and `tire_stale_hours`); `alerts.yaml` is read per model with a fallback to `config/defaults/alerts.yaml`. `make unmapped` and `make timezone` take the model. Code descriptions never fall back to another model: an unmapped code stays "unmapped" (CLAUDE.md rule: never invent titles).
- **Compatibility report (`make compat MODEL=cx60`):** compares what `views.sql` reads (signals as `signal = '…'`, `starts_with` families, ECU and warning kinds) with what the model's database contains, and lists the signals the views want but the model lacks and the signals the model has that nothing reads yet. This is how a new model is brought up without guessing, and it is the input for M28.
- **Alerts:** the engine runs per model database; `dedup_key` needs no model part because the databases are separate. Optional desktop notification titles include the model name.
- **Done when:** two temporary models with different data and different configs ingest side by side, and tests prove that alerts, code descriptions and time zones of one do not appear in the other.

**M22 as built.**
- **Most of M22's plumbing already existed from M21** (per-model paths, `--model` on every CLI, per-model config folders, the Makefile loops), so this milestone added what was still missing and proved the isolation with a test.
- **Isolation test** (`tests/test_model_isolation.py`): two models with different VINs, platform codes in the file names, warning codes, descriptions, time zones and alert rules are ingested and evaluated side by side; the test asserts that each database holds only its own VIN, that a description in one model is not used by the other (its code stays unmapped), that each uses its own `car_timezone`, and that alerts follow each model's own `alerts.yaml` and data.
- **Ingest warnings:** a model whose folder has no export files is reported (`warning: no export files for Mazda CX60 in ...`) and, when it has no database yet, none is created (an empty file would look like a model with data); a database that holds more than one VIN is reported with the VINs masked, because a model is one car.
- **Compatibility report** (`make compat`, `mazda_dash/compat.py`): for each model, how many of the signals the views read are in its data, which are missing (with the views they feed), which are present but never valid, the two warning-flag families (signals and how many change), which export kinds were loaded, and how many signals nothing reads (`--all` lists them, `--strict` exits 1 when something is missing). On the author's CX-5 all 39 named signals are present and 33 of 200 signals are read by no view.
- **Desktop notification** titles carry the model's name ("Mazda CX-5: 2 new alerts").
- **Differences from the plan:** (1) there is no shared `config/defaults/`: a missing `alerts.yaml` or `settings.yaml` already falls back to the built-in defaults (`AlertsConfig()`, UTC and 6 h), which is the same thing without a second copy that could drift; the CLIs print a note when a file is missing. (2) The report compares signals and export kinds, not ECU and warning kinds (those are data, not something the views require). (3) `make ingest` still runs one model per call and the Makefile loops over all of them; a single `--model all` option was not needed.
- **Checked:** backend 198 tests (8 new), lint, `make demo-ingest`, and `make compat` on the real database.

### M23 — API: choose the model ✅ done
- **Backend:** a `model` dependency (like `date_range`, in `api/models.py`) resolves the query parameter to a `Model` (default when omitted and only one exists or one is marked default; 404 with the list of valid ids otherwise) and `api/db.py` opens that model's file read-only; the alert write endpoints use the same resolution with the short read-write connection (503 while `make ingest` holds that model's lock). `GET /api/models` returns id, name, platform, hidden pages, whether the database exists and its data span, so the UI can show "no data yet" for a model whose folder is empty.

## Comparing models and periods, and fuel cost (M29–M34, built)

**Idea.** Pick two car models (say the CX-5 and the CX-60) and see the Trends metrics side by side. The numbers
already exist: `GET /api/trends/monthly?model=` answers per model since M23, so the first version needs **no new
API route** (two requests, one per model) and therefore nothing to mirror in the phone's TypeScript engine.
M28 (a real CX-60 export) is not a prerequisite: the synthetic CX-60 differs from the CX-5 on purpose, so the
feature can be built and tested now; M28 only decides later which metrics are fair to compare on real data.

### Is it useful, and what must it not claim?
Yes, for the metrics that describe **how the car is used or how it drinks fuel per distance**, and no for those that describe **how the car reports**:

| Metric | Across two models | Why |
|---|---|---|
| Distance, days driven, drives, time driving, average speed (per day) | comparable | they describe the usage; per day, so months of unequal length and different periods can be set side by side |
| Fuel consumption (l/100 km) | comparable **with a caution** | only like for like: a plug-in hybrid's l/100 km hides the electric part, and different fuels differ |
| Tire pressure (average, lowest) | caution | the recommended pressure differs per car |
| Warning events, read-outs with faults, new/distinct faults | caution | codes, how often the car logs them and what counts as a fault differ by platform |
| Different warnings (distinct codes) | not comparable | the code sets are different vocabularies |

So the page labels every metric *comparable* / *caution* / *not comparable* with the reason, never colours a difference
green or red (a different car is not an improvement or a regression), and never shows a guess as a fact (the
project's rule). Without those labels the page would invite wrong conclusions ("the CX-60 has far more warnings").

### Decisions (confirmed)
| Topic | Choice | Why |
|---|---|---|
| Where | a separate page `/compare`, not a mode of Trends | Trends is one car against its own previous month; comparing cars is another question, with its own caveats |
| Period | each car's own data, aligned by **calendar month**, by default only the months **both cars have complete** (a switch shows all data, and one for partial months) | different periods and partial months are the main way to compare unfairly |
| Basis | **per day** by default (the Trends "per day" maths, reused), and distance-weighted for l/100 km | totals depend on how long each car was observed |
| Wording | neutral and exact: "CX-60: 7.9 l/100 km, CX-5: 7.0, over 2 complete months (May–Jun)", with the difference as a plain percentage | no good/bad tones, always the number of months behind it |
| Backend | none in M29: two calls of the existing monthly route | no API change, nothing to mirror, no `make types` |
| Phone | M30, from small per-model summaries cached on the device | the phone's engine holds one pack at a time, so the other car's figures must come from somewhere else |
| Visible when | two models have data | like the model selector |

### Milestones
| | Milestone | Outcome |
|---|---|---|
| M29 | Compare two models (Mac) | `/compare` with two model pickers, a card per metric with both cars, comparability labels, an overlap or all-data switch |
| M30 | Compare on the phone | the same page offline, from per-model summaries cached in IndexedDB |
| M31 | Compare two periods of one car | the same page with "this period against that one" (this May against last May, before and after a change) |
| M32 | All cars at a glance | one card per model with its headline numbers (last reading, odometer, alerts, faults, next oil change), on the Mac and the phone |
| M33 | Estimated fuel cost | a fuel price per car in its settings, and "cost per 100 km" and "fuel cost (estimated)" next to the consumption everywhere it appears (Trends, Overview, Compare); recommended right after M29 |

Each milestone is implemented only on request, like the earlier ones. Order: M29 first (it holds all the design); then **M33**, because it changes the monthly answer (Python, TypeScript engine, goldens) and the phone's cached summaries of M30 should hold the cost figures from the start; then M30 and M32, which share the phone mechanism (cached per-model summaries); M31 reuses M29's logic and can come at any point after M29.

### M33 — Estimated fuel cost (cost per 100 km) ✅ done
**What it is, honestly:** an *estimate*, litres the car reports (the same estimate as "Fuel used (estimated)") times the fuel price **you** enter. It is not what you paid, and the dashboard says so wherever it shows the figure.
- **Configuration (per model, `config/models/<id>/settings.yaml`):** the price history, because fuel prices change and one fixed price would make old months wrong:

  ```yaml
  fuel_currency: EUR            # an ISO code; shown with Intl.NumberFormat
  fuel_prices:                  # price per litre from a date on; the last entry before a trip applies
    - {from: 2026-03-01, per_l: 1.72}
    - {from: 2026-05-15, per_l: 1.81}
  ```
  `fuel_price_per_l: 1.75` alone is accepted as one price from the start of the data. Without any price the cost metrics are empty and the cards say how to set one (never a made-up price). Validation like the existing settings: unknown keys, negative or non-numeric prices, an unknown currency, dates out of order are errors with the file name.
- **Data:** a new table `ref_fuel_prices(valid_from, per_l)` and the currency in `ref_settings` (loaded by `build_model`, like the time zone), carried by the **pack** (`TABLES` gains the table, so an older pack is refused with the existing "made by an older version" message and the phone has no copy of the values).
- **Maths (in SQL where possible, identical in Python and TypeScript):** the price of a month is the **average of the price in force on each trip, weighted by the litres of that trip** (the trip segments already carry litres); `cost_per_100km = l_per_100km × price` and `fuel_cost_est = fuel_l_est × price`, rounded like the other metrics, `None` for a month with no price or no consumption (a gap, not 0).
- **API:** two new fields on `MonthMetrics` (`cost_per_100km`, `fuel_cost_est`) and the currency (`currency` on the month rows). **Python API, TypeScript engine (`trends.ts`, `shapes.ts`), goldens and `make types` in the same change**, as the project's rule requires; the sample data of each model gets a price history (CX-5 in EUR with a mid-period price change, CX-60 with another price) so the goldens exercise it, including a month where the price changes.
- **UI:** two metrics in `trends.ts` (`cost_per_100km`: lower is better, `fuel_cost_est`: additive, per day) so they appear in Trends automatically, formatted with the currency; an Overview stat "about 7.2 EUR per 100 km" with the "estimate" note; in M29's `COMPARABILITY` table `cost_per_100km` is *comparable with a caution* (each car's own price and fuel).

## The car in 3D (M38–M41, built)

### Goal
A "The car" panel that draws the car in 3D with what its latest status reports say, each figure next to the part it belongs to. The user turns the car and looks at it from any side. Mac dashboard and phone app, offline on the phone like everything else. This is the first of the 3D ideas (status view); the others (time scrubber, who rides on the seats, alerts on the car, fault map, freeze-frame scene) would build on it and are not planned here.

### What it shows (only data the pages already have)
| Part of the car | Figure | Comes from |
|---|---|---|
| Each wheel | pressure in kPa, "old reading" mark when stale, a mark when the car's own tire flag for that wheel is on | `/api/overview` (`status.tire_*`, `tire_stale`), `/api/status/car-warnings` |
| Four doors, trunk, hood | closed / open / unknown, drawn ajar when open | `/api/doors/timeline?limit=1` |
| Locks | the raw codes as text (their meaning is undocumented) | same |
| Fuel tank | level % and range km | `/api/overview` |
| Engine bay | km to the next oil change, only for a car that sends the countdown; the oil-level flag | `/api/maintenance/oil`, car warnings |
| Dashboard | odometer, "as of" time of the snapshot | `/api/overview` |

Not shown, on purpose: battery voltage (the status reports do not carry it; it exists only in freeze frames), ECUs (their positions are not published), seat belts (a later idea), parking position (never leaves the Mac).

### Decisions (confirmed)
1. **A stylised car, built in code.** No Mazda mesh: none is freely licensed, and a file from a model site would be a licence and a size problem. The body is a generic SUV shape generated from a handful of dimensions (length, width, height, wheelbase, track, wheel size), so a CX-5 and a CX-60 differ in proportion, not in styling. No textures, no model files, nothing to download.
2. **Plain `three`, not react-three-fiber.** One dependency instead of three, no coupling to React's reconciler version, and no new peer-dependency trouble (`legacy-peer-deps`). The scene is one small class that React mounts into a `<canvas>`. (I mentioned react-three-fiber earlier; for a single scene it is not worth its weight.)
3. **Labels are HTML, not 3D text.** Each label is a DOM element positioned over the canvas from the projected 3D anchor of its part, with a leader line. So labels use the app's fonts and CSS variables, stay sharp, work in both themes and are readable by a screen reader.
4. **No new API route.** The panel composes the answers of four existing endpoints in a pure function, so there is no Python change, no engine twin, no golden and no pack change for M38–M40. (Only M41 touches the model list.)
5. **Loaded only when needed.** `three` goes in its own lazy chunk (about 150–200 kB gzipped; to be measured), fetched when the panel appears; the first paint of every page stays as it is. On the phone the chunk is in the build output, so the service worker precaches it.
6. **The 2D panel stays.** The same data as a plain list is built first (M38). It is the fallback when WebGL is missing or the context is lost, the accessible text equivalent, and what the tests check.
7. **Place:** top of the **Status** page. The Overview keeps its small 2D tire drawing (`Tires.tsx`) in this plan.
8. **Honest drawing.** Unknown or `Invalid` values are drawn as unknown (muted, dashed), never as closed or as zero. A door value of 0 is assumed closed, as today, and the panel says so. No thresholds are invented: a wheel is marked only by the car's own flag, the stale rule, or the existing "lowest by 20 kPa or more" rule of `Tires.tsx`.
9. **Motion and power.** The scene renders on demand (on a change, a drag or a resize), not in a loop, so an idle phone draws nothing. With `prefers-reduced-motion` nothing moves by itself: no turntable, doors are drawn open without the swing.
10. **Colours** come from the CSS variables (read from the document and re-read when the theme changes); no literals, so Dark and Light both work and `theme.test.ts` keeps its rule.

## More value from the same data (M45–M62, all built)

### Goal

### What the owner's data says about them (CX-5, 12 Jun – 10 Nov 2026; checked before planning)
- **Fill-ups are visible.** 240 status snapshots with a fuel level on 63 days; the level rises by 15 points or more between two consecutive snapshots **12 times** (58 points on average, 18 at the least), and only twice by a small amount (3 to 15 points) that could be noise or a slope. So a fill-up can be detected with a simple threshold, and the doubtful ones can be shown as doubtful.
- **Snapshots are uneven.** Half of them are within 1.6 hours of the one before, but one in ten follows a gap of 44 hours or more, and the longest gap is 262 hours. Everything below that is worded as "between two reports", and every forecast shows what it is based on.
- **Short trips dominate.** 214 trip segments, a median of 5.8 km, **47% under 5 km**: the driving-pattern page has something real to show.
- **Invalid values exist** (669 of 46,956 remote-status readings, 128 of 3,776 door readings): the data health page has a subject.
- **Four control units** report faults in this car: a fault map is small enough to place by hand.
- `ingest_runs` already records each load, which the "what changed" summary can build on.

### Decisions (confirmed 14 Nov 2026)
1. **Order:** quick wins and foundations first (units, data health), then the features that add insight (fill-ups, driving, the day page), then planning ahead (service log, leak forecast, maintenance forecast), then ease of use (import, report), then the 3D follow-ups from the cheapest to the one that needs the owner's input, then sharing, and the language last, so every string exists before it is translated once.
2. **Every milestone ships on the Mac and the phone together** where it shows data (the "keep both implementations in step" rule: Python route, TypeScript twin, goldens, `make types`). The exceptions are things only the Mac can do: importing Mazda's files (M53) and writing entries (M47, M50), which the phone shows read-only from its pack.
3. **Estimates are worded as estimates.** A forecast gives its figure, the period it was measured over and how many readings it rests on, and is withheld under a minimum; a detected fill-up says "between two reports"; nothing is presented as a fact the data does not hold.
4. **What the owner types in lives in files, not in the database:** the service log and the amounts paid go in `config/models/<id>/` (like the code descriptions and prices), so `make reset-db` never loses them and they travel in git if the owner wants. 5. **No new outside request, no new private data in the repository.** Uploading Mazda's download (M53) is to the API on the same machine only. Description packs (M61) hold descriptions, never a VIN or data.
6. **Sample data:** new demo data is derived from the clock and the odometer, never from new random numbers, so the committed CX-5 sample bytes stay the same unless a milestone says it must change them (then the goldens and the demo packs are regenerated in that milestone).
7. **One milestone at a time,** each started on the owner's word, each ending with tests, both builds, the docs and a commit.

### M51 — Tire leak forecast ✅ done
- **Maths (pure Python and the same in TypeScript, or one SQL):** per wheel, the difference between that wheel and the mean of the other three at each **measurement** (`v_tire_readings`, not snapshots), which cancels the temperature that moves all four together; a robust slope of that difference over the last N days (default 30, at least 8 measurements over at least 10 days, else no forecast); the date the wheel's own pressure reaches the limit (`low_tire_pressure.min_kpa` from `alerts.yaml`) at that rate; a refill (a rise of the wheel against the others) restarts the series.

**M51 as built.**
- **One SQL, shared:** `backend/src/mazda_dash/tires.py` (`FORECAST_SQL`, one parameter: the limit) and the same text in `mobile/src/engine/tires.ts` (compared character for character while building it). Per wheel: its difference from the mean of the other three at each **measurement** of `v_tire_readings` (known time, all four wheels read) in the last 30 days; a refill restarts the series (the wheel's own pressure up 25 kPa or more **and** 20 or more against the others between two measurements: both, because the car reports in steps of 5 or 10 kPa); the slope is a **Theil–Sen** estimate (the median slope over every pair of measurements at least a day apart), which one odd reading cannot move.

## Learning from the data (M63–M68 built; M69–M71 planned)

### Goal
Nine milestones that apply machine learning (clustering, anomaly detection, survival analysis, change points, robust regression, probabilistic matching, forecasting with ranges) to the data the dashboard already loads, to find patterns no fixed rule shows: which warnings belong together, which status reports are out of the ordinary, whether a fault tends to come back, whether the battery or the consumption changed, and what next month may cost. No new data source and no outside request. They came from the ideas of 17 Nov 2026; the owner asked for all of them as milestones. **None is started**: each starts on the owner's word, like every milestone before. M28 stays on hold.

### What the owner's data says about them (CX-5, 12 Jun – 10 Nov 2026; checked before planning)
- **Warnings:** 12,374 code occurrences at 7,802 moments on 64 days, 22 different codes. Cutting the moments wherever 10 minutes pass without a warning gives **247 episodes with 62 different sets of codes**, most of them near-copies of each other (`$210,$226,$290,$2CD,$2FE` 39 times, the same without `$2CD` 28 times): a similarity grouping (not exact sets) is what makes them readable (M63).
- **Status reports:** 258, uneven (half within 1.6 hours of the one before, the longest silence 262 hours). Status reports carry **no outside temperature and no battery voltage** (182 remote-status signals, none of them); fuel, odometer, doors, tires, belts and the car's flags are there (M64, M69).
- **Faults:** 111 fault readings in 36 read-outs, 16 codes; the most frequent (BCM `U0198`) is in 30 read-outs, most others in 3 to 17. Enough for a comeback curve on a handful of codes only (M67).
- **Freeze frames:** 37 frames at 16 distinct moments, each with `ECU_Power_Voltage`, `Main_ECU_Voltage_Supply`, `SOC_StateOfCharge`, `Ambient_Air_Temperature`, `Time_Since_Engine_Start`. The only source of voltage and outside temperature, and a thin one (M68, M69).
- **Stretches:** 214 between 13 Jun and 10 Nov, 192 of them between reports less than 48 h apart (M65, M66).
- **Tires:** 228 measurements of all four wheels (M69).
- **What was paid:** `fuel_log.yaml` is empty for this car and the service log has one entry: M70 has nothing to match on the owner's data until payments are logged; the demo data has them.
- **History:** five months. Nothing seasonal can be learned yet (M71 says so instead of pretending).

### Decisions (proposed, to confirm when each starts)
1. **Order:** what the owner's data supports best first (warning episodes, unusual reports), then the methods other milestones reuse (change points before the battery trend), then the ones that rest on thin data or on data the owner has not logged yet (fault comeback, battery, tire temperature, payments), and the forecast last, because it uses the others' results.
2. **Explainable methods over heavy models.** Five months of one car is a small sample: robust statistics (median, MAD, Theil–Sen as in M51), survival curves, change points, deterministic grouping. **No neural networks, no model files, no training on other people's data.** Every result says what it rests on (how many readings, over which days) and is withheld under a minimum, as the forecasts of M51 and M52 are.
3. **Both apps, one maths.** Where the method fits in SQL it is one SQL text shared by Python and the phone's engine (the M51 rule: change both together, goldens on both sample cars). Where it needs an iterative fit (change points, the routine grouping), it is fitted **at `make model` / ingest in Python** and stored in an `ml_*` table that the pack carries as an optional table (an older pack shows the page without that panel; no pack format change). Fits are deterministic: no random seeds that vary, no clock, no machine time zone.
4. **Hints, never verdicts or meanings.** An episode is "these codes usually appear together", never what they mean; an unusual report is "unlike this car's other reports", never a fault; a change point is "consumption changed around this date", never why. The wording modules get the neutrality tests of M48 and M36 (in both languages, M62), and **nothing is written into the owner's code descriptions by itself**.
5. **Alerts are opt-in.** Any new alert rule from these milestones is off by default in `alerts.yaml`, needs its `ALERT_PART` entry (M55) and its sentence patterns (M62).
6. **Sample data:** the CX-5 sample bytes stay as they are; where a feature needs something to show on the demo, it comes from the clock or a `Profile` flag of the CX-60 (the M37 rule).
7. **One milestone at a time,** each ending with tests, both builds, the docs (README, CLAUDE.md, the data dictionary for new views and tables) and a commit.

### M63 — Warning episodes ✅ done
- **Method:** cut the warning moments into episodes wherever `gap_minutes` (default 10, `settings.yaml`) pass without a warning; describe each episode by its set of codes; group episodes whose sets are alike (Jaccard similarity at or above 0.6, single-linkage, deterministic) into **patterns**, each with its *core* codes (in at least 80% of its episodes) and its *sometimes* codes. A code in nearly every episode (like `$210`) is listed once as "in almost every episode" and left out of the similarity, or it would join everything.
- **Where:** episodes as a view `v_warning_episodes` (gaps and islands in SQL, shared); the grouping is fitted at `make model` into `ml_warning_patterns` (pattern, codes, role) and `ml_episode_pattern` (episode, pattern), carried by the pack. `GET /api/warnings/episodes` (a period endpoint): patterns with how many episodes, on how many days, first and last, typical length, the faults read out within a day of them.
- **UI:** a "Patterns" panel on Warnings: one row per pattern (its codes with their titles where the owner has one, how often, a strip of when), and on the code-description flow a hint "usually appears with …" for an undescribed code. The Day page names the pattern of each episode.
- **Tests:** the gap rule across midnight and a silence; the always-present code; two patterns that differ by one code; determinism (same input, same patterns, any row order); an empty period; both sample cars (goldens).
- **Done when:** the owner's 247 episodes come out as a short list of patterns that can be checked against the raw rows by eye, and both apps agree.

**M63 as built.**
- **All in SQL, shared by both apps (changed from the sketch):** no `ml_*` table and no fit at `make model`. Four views in `views.sql` do it, and the phone rebuilds them from the same file: `v_warning_episode_sets` (episodes by gaps and islands; a code in 90% or more of all episodes, from 10 episodes on, is *common* and left out of the comparison), `v_warning_set_modes` (the grouping, a recursive CTE), `v_warning_episodes` (each episode with its pattern number) and `v_warning_pattern_codes` (each pattern's codes, `core` from 80% of its episodes, `sometimes`, or `common`). **No pack change, no `SUMMARY_VERSION` change**; `make model` after pulling.
- **Mode seeking, not single linkage (changed from the sketch):** linking every pair of sets with a Jaccard similarity of 0.6 or more chained 51 of the owner's 62 distinct sets into one group. Instead each set points to the most frequent set that is alike (itself included; ties: fewer codes, then the key) and follows those pointers to a set that points to itself; every set with the same end is one pattern. Patterns form around the sets that recur most, and a set alike to two others cannot join them (a test pins it).
- **Setting:** `warning_episode_minutes` in `settings.yaml` (whole minutes, 1 to 240, default 10), stored in `ref_settings`; documented in both models' settings files and the README.
- **Route:** `GET /api/warnings/episodes`, a period endpoint (`PERIOD_ENDPOINTS`, the golden matrix): `backend/src/mazda_dash/api/episodes.py` and, with the same SQL, `mobile/src/engine/episodes.ts`. Patterns and roles come from all the data, the period counts episodes by their start. It answers the gap, the common codes, each pattern in the period (episodes in the period and in all, recurring from 3 in all, days, first and last, the median length, its codes with role and share, the faults next to it) and each code's **companions**.
- **Faults next to a pattern, against a baseline (added):** on the owner's data BCM `U0198` is in 30 of 36 read-outs, so "read out within a day" put it next to every pattern. A fault is now listed only when it was read out within 24 hours of at least 3 of the pattern's episodes in the period **and** near a share of them at least 1.5 times its share of all the period's episodes; both shares are returned and shown.
- **The hint beside an undescribed code (changed):** the first version took the core codes of the pattern where the code was most present, which named codes that a rare code was seldom seen with. The route now gives each code's companions directly: the other codes in 80% or more of the episodes that hold it (from 3 such episodes, common codes left out). The Warnings table shows "not described yet · usually with $2FE". Nothing is written into the code descriptions.
- **UI:** `components/EpisodesPanel.tsx` on Warnings, between the chart and the code table: the headline, one entry per recurring pattern (its line, its codes as chips: "always" for core, "sometimes · 35%", "+N rarer" under 10%; a chip picks that code's events), faults that stand out, the common codes, what is not listed, and a note on how it is made. Wording in `frontend/src/episodes.ts` (neutrality tested in English and Portuguese), Portuguese in `i18n/pt/episodes.ts`.
- **Not done:** the Day page does not name an episode's pattern yet (it would change `api/day.py`, `day.ts` and `DAY_ENTRY` for a small gain); screenshots not retaken.
- **Real data (the owner's CX-5, 12 Jun – 10 Nov 2026):** 247 episodes; `$210` is in 98% of them and set apart; 7 recurring patterns hold 238. ### M64 — Unusual status reports ✅ done
- **Method:** per status report, a handful of features the car sends (fuel change per hour since the report before, distance per hour, hour of day, doors or trunk open, the tire spread, the car's own flags raised); each scored by a **robust z-score** (median and MAD of the car's own reports in the last 90 days), the report's score the largest of them, "unusual" from 3.5. One SQL, shared. An Isolation Forest was considered and left out: it would be Python only, random, and no better on 258 rows.
- **Route and UI:** `GET /api/status/unusual` (a period endpoint): the reports above the threshold with the feature that made each unusual and its value next to the car's usual range. Marks on the Day page and on the time scrubber (M56), and a short list on Status ("27 Sep 03:12: the fuel level fell 9 points while the car covered no distance; usually it changes by under 1 point an hour when parked").
- **Never a fault:** the text says "unlike this car's other reports", never a cause; a feature the car flagged Invalid is not scored. An optional alert `unusual_report` (off by default, part from the feature: fuel, door, wheel).
- **Tests:** a planted fuel drop and an open door at night are found; a car with constant values gives no division by zero (MAD of 0); Invalid values ignored; fewer than 30 reports = no scores; both sample cars.
- **Done when:** on the owner's data each marked report can be explained by looking at the Day page, and both apps agree.

**M64 as built.**
- **One view, shared by both apps:** `v_unusual_reasons` in `views.sql` (one row per reason a report stands out), so the phone rebuilds it from the same file: **no pack change, no `SUMMARY_VERSION` change**; `make model` after pulling.
- **Robust z-scores with a floor (changed from the sketch):** the owner's data is so regular that the median absolute deviation is 0 for most figures (the fuel level while parked almost never moves, the tire spread is 0 or 10 kPa), so a plain robust z-score divides by zero or calls every small step unusual. The scale is 1.4826 × the median absolute deviation **but never under the gauge's own step** (1 point of fuel, 5 kPa), and only the unusual side counts (a larger fall, a wider spread), from z = 3.5.
- **Rarity for what is not a number (changed):** a z-score of an hour of the day means nothing (23:00 and 00:00 are neighbours), and a door is open or not. The hour (the car's local time) and the set of open doors, trunk, hood and hazard lights are unusual when fewer than 1% of the reports of that kind share them; nothing open is never unusual.
- **The features as built:** `fuel_drop_parked` (points the level fell between two status reports while the odometer moved under 1 km; a rise counts as 0 and a fill-up pair is left out; from 10 pairs), `tire_spread`, `hour` (status and door reports separately), `open` (door reports). ### M65 — Consumption change points ✅ done
- **Method:** the consumption of the stretches (weighted by distance, a stretch from 5 km), as a series in time; change points found by **binary segmentation with a penalty** (a split is kept only when it lowers the cost by more than the penalty and each side holds at least 150 km and 10 stretches). Fitted in Python at ingest into `ml_change_points` (`series`, at, before, after, the km each side rests on), carried by the pack. Written so M68 can reuse it for the voltage series.
- **UI:** dashed vertical marks on the Trends consumption chart and a line under it ("around 14 Sep the consumption went from about 7.1 to 7.9 l/100 km; 1,240 km before, 980 after"), with the service-log entries, fill-ups and the share of short stretches (M48) next to it **as context, never as a reason**.
- **Tests:** a planted step is found within a few stretches; noise without a step gives none; short sides are refused; the penalty is deterministic; the units of M45 shown, the maths in l/100 km.
- **Done when:** the demo's planted step (a `Profile` flag of the CX-60) is found, the owner's series gives none or a step visible on the chart, and both apps show the same marks.

**M65 as built.**
- **Python and TypeScript, not a stored fit (changed from the sketch):** binary segmentation needs a loop that SQL does badly, but it is small and pure, so it is written twice, line for line: `backend/src/mazda_dash/changepoints.py` (`segment`, `noise`) and `mobile/src/engine/changepoints.ts`, with the same order of operations so the floating-point sums agree (the contract replays it on both sample cars, the CX-60's two segments included). No `ml_*` table, **no pack change, no view change**. Written to be reused by M68.
- **The method:** the series is every stretch of 5 km or more whose reports are under 48 h apart (the stretches M48 puts in a band), its l/100 km weighted by its km. A segment's cost is the weighted sum of squares around its mean; the best split is kept when the gain is above `PENALTY × σ² × log n`, each side has 10 stretches and 150 km, and the means differ by 0.3 l/100 km; both sides are split again. σ² is robust: from the differences between neighbouring stretches (median of squared differences over the chi-square median), so a step does not inflate it.
- **The penalty, measured (added):** on series shaped like the sample's (160 stretches, sd 0.5) a penalty of 3 gave a false change point on 1 flat series in 6. **7** gives 1 in 100, finds a 0.9 l/100 km step 199 times in 200 (exactly one change point) and a 0.5 step two times in three.
- **Route:** `GET /api/trends/change-points`, a **state** endpoint (learned from all the data, like M63 and M64): `api/changes.py` and `mobile/src/engine/changes.ts`. The segments (from, to, stretches, km, l/100 km, and the share of ALL their classified stretches under 5 km), the minimums, and `enough`. A change point is where one segment ends and the next begins.
- **UI (changed from "marks on the Trends chart"):** the Trends cards are monthly bars, where a date inside a month cannot be marked cleanly, so it is a panel of its own, "Steps in consumption", before "How the car is driven" (`components/StepsPanel.tsx`): the headline, the level as steps over time with a dashed line at each change (drawn only when there is one), and per change a sentence (around when, from and to what level, the distance each side), the share of short stretches before and after, and the service-log entries within two weeks: context, never a reason. **Fill-ups were left out** of the context: there is one every couple of weeks, so one is always "near". Wording in `frontend/src/steps.ts` (when, never why; neutrality tested in both languages), Portuguese in `i18n/pt/steps.ts`; the maths stays in l/100 km and only what is shown is converted.
- **Demo data:** the CX-60 profile has `l100_step = (10 Jun 2026, +0.9)`: from that day every drive uses 0.9 l/100 km more (no new random number). It moves when the car refuels, and a refuel draws its fill level, so the rest of the CX-60's sample changed too (regenerated, with its goldens; the CX-5's sample bytes are unchanged). Found: 7.9 → 9.18 l/100 km between 9 and 10 June.
- **Found while checking, and fixed:** `make demo-ingest` loaded new sample files on top of the existing demo database, so after the CX-60 sample changed, an old `db/demo-cx60.duckdb` held both versions (and showed two steps over 12,000 km). - **Real data (the owner's CX-5):** 101 stretches, 3,666 km: no step stands out; about 6.6 l/100 km throughout, 47% of stretches under 5 km.
- **Tests:** backend 11 in `test_change_points.py` (flat, one step and where, two steps, the minimums, a robust noise, empty and tiny, determinism, short shares and the 48 h rule on a stand-in table, too little driving, nothing, both sample cars) and the rest unchanged (510 in all); frontend 8 in `steps.test.ts` (457); the phone contract replays the route on both cars (1,149).

### M66 — Driving routines ✅ done
- **Method:** each stretch described by its length (log), duration, weekday or weekend, and the hour it started; grouped by **k-medoids with a fixed start and k chosen by silhouette** (2 to 6), fitted at ingest in Python into `ml_routines` and `ml_stretch_routine`, carried by the pack. A routine is kept only with 8 stretches on 4 different days; the rest is "other".
- **UI:** a "Routines" panel on Trends after the driving pattern (M48): each routine in words ("weekday mornings, about 18 km in 25 minutes; 41 stretches"), its share of the distance, its consumption from 20 km summed, and a small chart of when it happens. The Day page names a stretch's routine.
- **Words:** a routine is a kind of stretch, never a place (no GPS is used or inferred) and never a judgement of the driver (the M48 test words).
- **Tests:** two planted routines are separated; determinism; the minimums; a car with too few stretches shows nothing; both sample cars.
- **Done when:** the owner's 192 stretches give routines the owner recognises, or the panel says there are too few, and both apps agree.

**M66 as built.**
- **Python and TypeScript, not a stored fit (changed from the sketch):** like M65, no `ml_*` table and **no pack change**: `backend/src/mazda_dash/routines.py` and `mobile/src/engine/routines.ts` are the same algorithm line for line. Python and the browser can differ in the last bit of `log`, `cos`, `sin` and `atan2`, so every feature is **rounded to 9 decimals on both sides** (and Python's `%` is copied exactly, `pyMod`). Checked beyond the sample cars: the phone engine replayed on the owner's own database (from the session scratchpad, never in the repository) matched Python in all 654 cases.
- **The features (changed):** the length (`log(1 + km)`, standardised), the time the stretch **ended** in the car's local time on a 24-hour circle (cosine, sine), and weekend or not. Not its start: a stretch starts at the report before it, which can be hours earlier. Not its duration: the trip computer's driving time is sometimes negative (a reset between reports); it is only described, from the positive ones.
- **The method:** k-medoids with PAM's BUILD start (deterministic) and alternating steps instead of PAM's swaps (fast enough as the data grows: 0.03 s for 192 stretches); k from 2 to 6 by the mean silhouette. A group is a routine with 8 stretches on 4 different days, and only when the grouping is clear (silhouette 0.25 or more); the rest is "other". Nothing is tried under 30 stretches.
- **Route:** `GET /api/trips/routines`, a **state** endpoint (all the data): `api/routines.py` and `mobile/src/engine/routinesroute.ts`. Each routine: stretches, days, km and share of the distance, median length and driving time, weekend share, typical end hour (circular mean) and its 10th–90th percentile range, and a consumption from 20 km (stretches with a negative fuel figure left out, found on the owner's data); the other stretches; and each stretch's routine (for the Day page).
- **UI:** `components/RoutinesPanel.tsx` at the end of Trends: the headline, each routine as a title from the days, the part of the day and **its typical length** ("On weekdays in the evening, about 6.4 km": without the length the owner's data had two routines with the same name), a line, a bar of its share of the distance, the stretches that fit none, and a note. The Day page adds "closest routine: …" under a drive, matched by the end of its stretch (the drive's `until`: its `at` is the report before). "Closest" because each stretch joins the routine it is most like, so a Friday stretch can be in a routine of weekends. Wording in `frontend/src/routines.ts` (never a place, never a judgement of the driver; tested in both languages), Portuguese in `i18n/pt/routines.ts`.
- **Real data (the owner's CX-5):** 192 stretches, six routines, silhouette 0.33: weekday evenings ~6 km (51 stretches), weekend mornings ~10 km (50), weekend short hops ~0.7 km (36), weekend middays ~12 km (22), weekday morning short hops ~0.9 km (21), and long trips ~280 km (12, 71% of the distance). The demo cars each give their three planned routines (silhouette 0.74 and 0.76).
- **Tests:** backend 13 in `test_routines.py` (three kinds found, the hour on a circle, determinism, too few points, the median; on stand-in tables: the description and numbering, local time, a small group as other, too few stretches, a negative fuel figure, the 48 h rule, no driving; both sample cars) and the rest (523 in all); frontend 9 in `routines.test.ts` (466); the phone contract on both cars (1,151) and on the owner's database (654).

### M67 — Fault comeback ✅ done
- **Method:** per fault code and control unit, each read-out where it is no longer reported starts a wait; the wait ends when it is read out again, or is cut off at the newest read-out (censored). A **Kaplan–Meier curve** in SQL (shared): the share still not back after 7, 30 and 90 days, and the median wait when the curve reaches it. Shown only for a fault with 3 waits that ended, else "too few cases".
- **Route and UI:** `GET /api/dtcs/comeback?ecu=&dtc_code=` (a state endpoint) in `FaultDetail` under the freeze-frame summary ("after it stopped being reported, it came back within 30 days 4 times out of 6; a read-out after a workshop visit is marked"); the service-log visits (M50) are drawn on the curve's time line. A line in the report for the workshop (M54).
- **Tests:** a fault that always returns, one that never does (all censored), one with a single wait; a read-out on the same day; both sample cars.
- **Done when:** the curves for the owner's `U0198` and `U3000` agree with a hand count of the read-outs, and both apps agree.

**M67 as built.**
- **SQL for the read-outs, the walk and the estimate in code (changed from "a Kaplan–Meier curve in SQL"):** the read-outs come from one SQL query; walking each fault's read-outs and the Kaplan–Meier estimate are a few loops in `api/comeback.py` and, the same, `mobile/src/engine/comeback.ts`. Only sums, products and divisions, so Python and the browser cannot differ in the last bit. **No view, table or pack change.**
- **Per unit, only the read-outs where it answered:** a unit's read-outs are those where it reported `none` or `fault`; a read error says nothing about its faults (on the owner's data a unit answered in about 45 of the 54 read-outs). A wait starts at the first read-out without the fault after one with it, and ends at the next that lists it again; one still open at the unit's newest read-out is censored there.
- **Route (changed from one fault per request):** `GET /api/dtcs/comeback` is a **state** endpoint that answers **every** fault ever listed at once (its read-outs, how often listed, first and last, whether the newest read-out lists it, its waits, and from 3 waits that ended the share still not back after 7, 30 and 90 days and the median wait), so the fault page and the workshop report share one request.
- **The plain history is shown too (added):** on the owner's data no fault has three returns: BCM `U0198` stopped three times and came back twice (after 49 and 9 days), every other fault stopped once and was never listed again. - **UI:** "Comes back?" The workshop report adds one line per fault ("listed in 30 of 43 read-outs; stopped 3 times, listed again after 49 days and 9 days; …", "stopped once, not listed again"). Wording in `frontend/src/comeback.ts` (never "fixed", "failed" or a cause; tested in both languages), Portuguese in `i18n/pt/comeback.ts`.

### M69 — Temperature-aware tire pressure
- **Method:** the leak forecast of M51 already cancels what moves all four wheels together; what is left of the cold mornings is the wheel that warms or cools faster. Fit, per wheel, the remaining difference against the **hour of day and the month** (the status reports carry no outside temperature; a freeze frame's `Ambient_Air_Temperature` is used when one is within an hour, which is rare), take that pattern out, then run the same Theil–Sen forecast. In the shared `tires.py` / `tires.ts` SQL.
- **UI:** none new: the M51 lines and the alert use the adjusted series; the line says "after allowing for the time of day" when the adjustment moved the rate by more than 1 kPa a week.
- **Tests:** a planted morning dip on one wheel no longer looks like a leak; a real leak survives the adjustment; the M51 tests keep passing on the unadjusted cases.
- **Done when:** the demo's leaking wheels keep their rates, a CX-60 `Profile` flag with a morning dip gives no false leak, and the owner's (non-leaking) wheels still say nothing.

### M70 — Fill-up matching
- **Method:** replace M47's "earliest fill-up whose two days span the payment" with a **score** per payment and candidate fill-up: the days between them, the litres paid against the litres seen (when both exist), the level rise; each payment goes to the best candidate (one-to-one, ties by time), and its confidence (high, medium, low) is shown. In the shared `refuels` SQL.
- **UI:** the confidence in the Fill-ups table; a low-confidence match is listed with the payment and the fill-up side by side for the owner to check; unmatched payments stay listed.

- **Done when:** the demo's payments match as the generator wrote them, and the owner's fill-ups match as soon as payments are logged.

### M71 — Monthly forecast with ranges
- **Method:** next month's distance, litres and estimated cost as a **range (10th to 90th percentile)** by resampling the car's own days (blocks of a week, to keep weekly habits together) from the last 90 days, the price in force on the newest day, the consumption of the last 90 days (or after the last M65 change point, when there is one). **No seasonality until 12 months of data exist**; then the same month a year before is blended in, and the page says which was used. Fixed resampling order, so the answer is deterministic. In SQL, shared, or fitted at ingest if the resampling is too heavy for the phone.
- **Route and UI:** `GET /api/forecast/month` (a state endpoint) and a line in the Overview's "Looking ahead" panel (M52): "next month, at this pace: 900–1,350 km, about 70–100 l, 120–180 EUR (from the last 90 days)". A calendar entry is not added.
- **Tests:** a steady car gives a narrow range; a car with long silences gives a wide one and says so; no price, no cost; under 30 days with data, nothing; both sample cars.
- **Done when:** the range for a past month, built from the 90 days before it, can be checked against what that month really was on the owner's data.

### Risks
| Risk | Plan |
|---|---|
| Five months of one car is a small sample; patterns may be noise | minimums on every result, the basis shown, "few cases" cautions, robust methods only |
| A pattern or an unusual report is read as a diagnosis | neutral wording tests in both languages; hints never written into the code descriptions |
| Python and the phone compute different numbers | shared SQL where possible; fits stored in `ml_*` tables carried by the pack otherwise; goldens on both sample cars |
| Fits change from one run to the next | deterministic methods, fixed starts, tie-breakers in every `ORDER BY` |
| Freeze frames are a biased sample (taken only with a fault) | said on the battery panel; no claim about the car's life in general |
| The demo data cannot show a feature without changing the CX-5 bytes | `Profile` flags on the CX-60 only, derived from the clock |

## Open questions

- **Meaning of the `$xxx` warning codes, the DTC status flags, the alarm codes, the non-zero values of the car's own warning flags and the 128 warning-lamp flags.** Still open: Mazda does not publish them. `$210` appears in ~98% of events and is probably informational, but that is a guess. Descriptions are meant to be filled in by the owner in `config/codes/`; the dashboard offers hints (what appears around a flag) as a starting point.
- **Time zone of `COPIED_DT_TM` / `fileid_datetime`.** Assumed UTC (the diagnostic tool dump states its own offset, which is applied). The tire measurement clock is the car's *local* time and has its own setting (`car_timezone`, M19).
- **Several vehicles.** Different models are supported (one database, folder and configuration each); two cars of the *same* model are not separated (one car per model folder, `make ingest` warns about a second VIN).
- **Other models, markets and firmware.** Only one real export (a CX-5, Europe, 2026) was available; others may differ. Multi-model support is built (M21–M27); what a real CX-60 export needs is M28, not started.
- **What is fair to compare across models?** Proposed in "Comparing models and periods" (usage per day, fuel per distance with a caution); the real answer needs a real CX-60 export (M28), in particular for a plug-in hybrid's consumption.
- Resolved: the warnings table is mostly repeats of the same few codes, so alerts are based on new codes and unusual days, not on every row.
